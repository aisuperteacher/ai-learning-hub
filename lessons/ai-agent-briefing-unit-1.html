如果我手工读三份资料就能完成，为什么还要做 AI 应用？

手工方法完全可以完成。资料都很短时，把全部正文交给一次模型调用，也可能足够。开发应用的价值在于把重复的输入、资料准备、结果整理和核查组织起来；是否值得自动化，要看重复频率、输入变化和错误代价。

本轮为了看清 Agent 的结构，额外演示“先只给目录，再按需要读取正文”。这是教学安排，并不表示三份短资料必须使用 Agent。

02 / 同一条请求的全貌

谁负责决定，谁负责执行，谁负责核查？

应用程序就是按开发者编写的规则运行的软件。本场景里，它接收关注点，准备给模型的信息，执行允许的读取操作，保存过程，再展示结果。语言模型根据收到的信息生成回答，或提出需要执行的动作。工具是应用暴露出来的一项具体能力，这次只有“按编号读取资料”。

应用程序控制真实执行：维护允许的工具、检查参数和预算、保存结果、发起下一轮模型调用。模型提出请求后，仍要经过这一层。

完整走一遍：你提交关注点 → 应用给出任务、A/B/C 目录与工具说明 → 模型请求读 A → 应用检查并执行 → A 的正文回传 → 再判断是否读 B → 根据已取得正文生成候选简报 → 应用核对 → 你看到有出处的结果。

真实产品常有前端和后端：前端是在浏览器里让你输入和查看结果的部分；后端负责受控执行、访问模型服务以及保存任务状态。本页把实验放在浏览器里，便于离线观察。真正接入模型服务时，应把服务凭据和执行权限放在受控的服务端环境。

做法谁安排下一步这个场景的例子
一次模型调用应用一次准备好输入直接给三份正文，请模型筛选并整理。
工作流 Workflow主要路径由代码预先安排固定读 A/B/C，再筛选、总结、核查；也可以有分支和循环。
Agent（本课采用的定义）模型在允许范围内，根据结果选择下一动作先看目录，选择读哪份；读到“详见迁移说明”后再决定补查；资料足够时结束。

AI 应用是总称，工作流和 Agent 可以组合使用。这里采用一种常见架构区分，行业命名并不完全一致。是否有聊天界面、是否用了工具、是否有循环，都不足以单独定义 Agent。[1]

03 / 进入局部，始终记住原任务

本轮只拆开五个核心机制

机制一：把任务变成模型实际收到的信息

在原图中，位置是“应用 → 模型”。提示词 Prompt是给模型的任务说明与约束。它需要明确“做什么、参考什么、怎样输出、缺信息怎么办”。

任务：从所给资料中，挑出与 Windows 使用、API 接入有关的变化。
数量：最多两条，不要求凑满。
每条字段：变化、影响、建议动作、来源编号、原文依据、未知项。
依据：事实仅来自已取得的正文。
区分：影响是推断，行动是建议，均明确标注。
缺失：原文没写，写“未说明”；读取失败，报告缺口。
资料：A/B/C 目录，以及随后读到的正文。
可用动作：read_doc(doc_id)，只读，不发布。

为什么不能只写“帮我总结一下”？因为“相关”需要一个判断标准，“最多两条”与“必须两条”会导致不同的选择，事实和建议也需要分开。明确约束能减少歧义，但约束写在提示词里，不等于程序已经保证执行。数量、工具名单和预算等可检查条件，还要由程序落实。

回到场景：若任务改为“只关注外观”，C 会变得相关；原文并没有变化，变的是任务标准。模型负责按标准处理文字，应用负责把正确标准交给它。

机制二：资料“存在”，与模型“收到”，是两个状态

上下文 Context是本次模型处理时实际可用的信息，包括任务、工具说明、相关历史和工具结果。资料在文件中、网页上，或者应用刚刚读到，并不表示它已经进入模型本次输入。[3]

时刻应用程序有什么模型被提供了什么
开始资料库和任务任务、目录、工具说明；没有正文
本地读取 A 后A 正文、读取结果尚未自动增加 A 正文
回传 A 并再次调用后A 正文和过程记录本次输入包含 A 正文，可据此继续

状态 State是应用保存的任务进度，例如已读资料、调用次数、错误和候选结果。应用从状态中挑选必要内容组成上下文。两者有关联，但不完全相同：程序可能保存所有日志，下一轮只发送相关部分。

回传正文的作用是补充本次可用证据。这不等于重新训练模型，也不自动保证模型永久记住资料。若把 A 正文漏掉，应用即使读过，也不能把随后输出的 A 结论当成已经基于这次读取完成核查。

机制三：工具调用先是一份请求，随后才有执行

Tool Calling / Function Calling（工具调用 / 函数调用）让模型提出一项结构化请求。本轮使用自己实现的工具，因此由应用检查并执行。托管工具也可能由服务商执行；这里学习的是自定义工具的一次来回。[2]

下面是本课简化的教学消息格式，不是任何厂商 API 的原样格式：

{
  "type": "tool_call",
  "call_id": "call_1",
  "name": "read_doc",
  "arguments": { "doc_id": "A" }
}

JSON是一种用“字段名 : 值”表达数据的文本格式。花括号表示一组字段。这里的 name 指定能力，arguments 是传给这项能力的参数；doc_id 指资料编号。call_id 是这一次调用的编号，方便把返回结果与它配对，和资料编号不是同一个东西。

应用收到请求后检查：工具名是不是允许的 read_doc；参数是否只有一个合法的资料编号；本次任务还剩多少读取次数。检查通过，才执行读取函数，并返回正文或错误：

{
  "type": "tool_result",
  "call_id": "call_1",
  "result": {
    "ok": true,
    "doc_id": "A",
    "body": "DemoCLI 修复 Windows 安装路径包含空格时启动失败的问题……"
  }
}

“模型说请读 A”时，没有正文；“工具真的读出 A”后，才有执行证据；“结果回到下一轮输入”后，模型才能使用新证据。工具说明负责告诉模型怎么提出请求，执行函数和权限检查则是另外的程序逻辑。

机制四：循环根据结果继续，也必须能够结束

Agent 循环可以概括为：看任务和已知结果 → 提出下一动作 → 应用执行 → 得到新结果 → 再决定。关键是新结果参与下一步决定，而不是无限重复调用模型。

在我们的正常演示中：读 A → 收到 A → 读 B → 收到 B → 提交简报。若 B 失败，结果就是“B 读取失败”，不是 B 的正文。应用可以结束并说明缺口，也可以在明确规则内有限重试；本轮选择前者，便于看清依据边界。

本课的预算：maxCalls = 2 表示最多实际执行两次工具。执行 A 和 B 后，仍允许生成最终答复；“模型轮数”和“工具次数”不是一个计数。真实应用还要按需要限制模型调用次数、总时间和费用。

如果模型要求一个未开放的 publish_brief（发布简报）工具，应用应阻止执行。本课任务只允许读资料，输出一句“已发布”不能替代实际操作证据。

回到场景：是否应该结束，要看目标所需证据是否足够、是否存在错误以及是否触及限制。循环和停止规则都是应用的一部分；框架可以帮忙实现，但不能替代这些设计判断。

机制五：格式正确、来源存在、结论有据，需要分别检查

结构化输出是把结果组织成固定字段与类型，方便程序读取。例如每条都包含变化、影响、动作和来源。部分模型服务可以通过约束输出结构来提高格式可靠性，但仍要处理服务异常与拒绝等分支。格式符合约定，并不直接保证内容真实。[4]

检查层本轮怎么查仍然不能证明
格式条数不超过两条；必要字段存在每条事实都正确
可追溯性来源来自成功回传的资料；摘录确实在正文中结论没有夸大原意
事实与任务对照原文核查变化范围、未知项与相关性未来所有资料都能正确处理

例如“B 提到新接口使用新参数”有依据；把它写成“旧接口今天全部停用”，即使末尾也写 来源 B，仍然越过了证据。实验页的程序能检查字段与摘录，最终的语义核对仍要对照原文。

06 / 回到最初那份简报


用同一任务验收，再处理一个变化


现在回到最开始的要求，逐项检查最终结果，而不是只看它是否“生成了一段文字”。下表记录本课设计的可观察结果；你的操作与解释仍需要实际完成后才有证据。


输入条件应观察到什么需要解释的原因


默认正常，预算 2A/B 两条，工具执行 2 次；规则替身 3 轮两次读取之后，还需要一次生成最终答复的决定


B 超时，预算 2保留 A，B 明确缺资料，结果为部分完成一次执行可以返回错误，错误不能当作正文


漏回传，预算 2本地读取发生，但没有可用正文进入消息；最终缺证据并停止应用拥有信息与模型收到信息不同；此重复行为由教学规则预设


预算 1只取得 A，B 缺失；仍能结束并报告部分依据工具预算限制执行次数，不应该阻止最终状态说明


请求发布工具被拦截，实际工具执行 0 次，任务未完成模型请求不能扩大应用实际开放的权限


关注点改为外观只读取并整理 C“相关”依赖任务目标，而非固定排斥某份资料




两种“通过”要区分：程序检查通过，只表示本次输出符合已编码的规则。资料失败时，“诚实报告缺口”可以通过规则核对；但本次任务仍有一份相关资料未成功读取，因此结果属于部分完成。






先看一个提示
看 B 的工具返回值：ok 是真还是假？消息里有没有正文？执行次数在统计动作发生了几次，还是正文取得了几份？


完成尝试后，查看参考解释
应保留 A，并说明 B 读取超时，无法基于 B 正文给出结论。A 和 B 的读取都确实执行过，所以执行次数是 2；B 的结果是错误，没有正文，因此只有 A 能作为资料依据。重复引用“来源 B”不会让缺失的正文出现。
下一步若要重试，需要明确重试规则与次数限制，并再次取得真实结果。本实验没有自动重试；只把预算加大，也不会自动修好一个没有设计的恢复流程。






记录只保存在当前浏览器，本地文件的存储可能受浏览器限制，不保证跨设备保留。顶部完成按钮只记阅读完成。导出的续学卡可带回对话；理解、操作与迁移能力仍须依据你的回答或产物判断。
