03 / 为什么一个事务包不住

两处修改，
没有同一个“提交按钮”。

一次改价，跨了数据库和 Redis。中间可能断网、崩溃，也可能插入另一个请求。

数据库边界
更新商品价格
提交 / 回滚
管理本数据库的修改
⋯
Redis 边界
SET / DEL
操作缓存
原子执行不跨到数据库
数据库事务提交成功，不代表 Redis 的删除也成功。
“双写”也包括：改数据库 + 删除缓存。两边状态都需要改变。
为什么一定说“数据库提交后”再删除？

如果事务还没提交就删缓存：读请求可能查到数据库中仍已提交的旧价格，再把旧价回填；随后新价格才提交。把 DEL 写在一个 @Transactional 方法的最后，也不自动等于在事务提交之后。

数据库事务、Redis 事务以及 Lua 的边界不同；普通用法不会自动提供跨数据库与 Redis 的原子提交。

    数据库为准 + 提交后失效 + 持久重试 + TTL 兜底。
    最终一致性：允许短暂旧值；在变更停止、在途旧请求结束，且重试 / 过期与主库回源能够正常完成等条件下，最终恢复。
    强一致性的直观要求：一次写成功后才开始的读，应看到该写或更晚的结果，需要更严格的完整协议。
    这张待办解决了什么，还没解决什么？

    它封住“数据库已经提交，却没来得及留下重试任务”的缺口。待办处理成功后再确认完成；重复执行 DEL 可以接受，但多次删除之间仍可能有人回填。

    它不自动消除旧读回填，也不让两个系统同步提交。可靠重试还需要任务扫描、失败告警与恢复。更低陈旧容忍度需要更严格的回填协议。

    另一条路是 CDC（变更数据捕获）：从数据库提交日志发现变化，再触发缓存失效。多系统、脚本都能改数据库时，尤其要考虑变更覆盖范围与消费延迟。

    06 / 三个常见误会

    这些工具有用，
    但每个都有边界。

    TTL = 这份缓存还能活多久。
    不是“数据库改了多久”。
    示例：TTL 设为 30 秒，旧值却可能在提交 20 秒后才被回填。

    在没有继续回填旧值、没有刷新旧缓存 TTL，且后续读取主库等条件下，过期能帮助恢复。不能只凭 TTL 就承诺“提交后最多陈旧 30 秒”。30 秒仅用于演示。

    删一次 → 改库 → 等一会 → 再删。
    第一次删→数据库提交→第二次删
    如果拿着旧值的读请求，在第二次删除之后才回填呢？

    延迟双删能覆盖一部分竞态；固定等 500 毫秒没有普适保证。进程暂停、慢查询、网络抖动都可能超过等待时间，第二次删除本身也可能失败。延时任务还要能持久重试。

    01

    只锁写请求

    挡住两个写者互相覆盖；没有自动挡住读请求的旧值回填。

    02

    读写都协调

    相关读、写、回填必须遵守同一协议；还要处理锁失效、超时与吞吐损失。

    03

    版本屏障

    拒绝比当前版本更老的回填；只在值里带 version 不够，删除后也要保留有效的版本屏障。

    这些是更严格设计的方向；“加个分布式锁 / 加个版本号”本身不构成完整保证。
    07 / 从业务决定允许多旧

    先问：读到旧值，
    会发生什么？

    同一份商品数据，在“展示”和“成交”时可以使用不同的读取路径。

    ▱

    商品列表：业务允许短暂旧价

    可从 Cache-Aside + 可靠失效 + TTL 起步。先确定可接受的陈旧程度，再验证并发、重试延迟与回源压力。

    ✓

    最终成交、余额或库存校验

    把关键判断放在权威数据库的事务 / 条件更新中。读主库本身仍不等于所有业务约束都正确；并发扣减也要由事务与条件约束保护。

    ↩

    用户刚改完，自己立即要看见

    本次返回已提交的新值，或为该次读取走主库。这实现了特定路径的需求，不自动保证其他客户端也立即读到新值。

    需要“写成功后，后续读取都看到最新值”，就要设计并证明相应的读写协议。

    若使用数据库只读副本、多级缓存或长事务快照，还要继续分析它们各自的滞后。缓存里“看上去还有库存”不能成为成交的最终依据。

    08 / 用自己的话讲一遍

    学会的标志：
    你能指出旧值怎么留下来。

    读

    先缓存，未命中查库

    从可靠的数据源回填，并原子设置缓存值与 TTL。

    写

    先提交库，再失效缓存

    删除让后续未命中从数据库重建，减少直接更新缓存的交错问题。

    补

    可靠重试，过期兜底

    面向最终恢复；仍须单独处理严格一致性与旧值回填。

    回到实验室 · 选择“旧读回填”

    两步写都成功了，缓存为什么还是旧的？

    先自己说三句话：读请求何时拿到旧值？写请求何时提交和删除？旧值何时回填？

    A 在改价提交前，从数据库读到了 100，但还没写缓存。B 提交 120 并成功删除缓存。A 随后才把手中的 100 回填，所以下一个读请求会命中旧价。

    再删可以修复这一次；可靠重试和 TTL 帮助最终恢复。若不能接受这种窗口，就需要覆盖读、写、回填的协调或版本屏障等协议。
    开发者视角：最小流程伪代码
    读取商品：
  value = Redis.GET(key)
  if value 存在：return value
  value = 数据库主库.READ(id)
  尽力执行 Redis.SET(key, value, EX=ttl)  // 值和过期时间一起设置
  return value

修改商品：
  数据库事务 {
    UPDATE 商品价格
    INSERT outbox(失效此 key)           // 同库、同一个事务
  } // 确认提交成功
  尝试 DEL(key)                         // 缩短常见窗口

待办处理器：
  读取未完成待办
  DEL(key)
  成功后确认完成；失败保留并重试、告警

边界：这段流程仍允许旧读回填；严格要求另设完整协议。
