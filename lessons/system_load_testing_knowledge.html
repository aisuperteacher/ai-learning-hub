系统压测知识体系
与核心原理

我们不从 JMeter 按钮开始，而是先弄明白：流量怎么进来，系统为什么变慢，以及怎样判断它真正扛得住。

先记住一句话：压测不是“把并发调到最大”，而是用可控制的流量，证明系统在指定业务场景下的速度、正确性和稳定性是否达标，再找出限制它的环节。

01 先建立一张知识地图

系统压测究竟在测试什么？

假设有一个“查询订单”的接口：客户端发请求，流量穿过网关，进入应用服务，最后查询 Redis 或 MySQL。

施压器模拟用户和请求
→

→

观察：每秒进入多少请求 → 每秒成功完成多少 → 各请求等了多久 → 哪一段在排队或报错。
① 明确目标业务场景、SLO、环境与数据
② 设计负载VU、到达速率、流量比例、变化节奏
③ 记录指标RPS、RT、P95、错误、饱和度
④ 归因与复测CPU、线程、连接池、慢 SQL、优化验证

02 第一组：流量与并发

VU、并发、RPS、QPS、TPS 到底差在哪？

VUVirtual User · 虚拟用户

模拟一个用户按脚本执行操作；可能正在等响应，也可能在“思考”或暂停。100 VU 不等于 100 个在途请求。

并发请求数In-flight Requests

某一时刻已经开始、尚未结束的请求数量。用户数、线程数和并发请求数不是同一概念。

RPSRequests Per Second

每秒请求数。要说明统计的是发送、到达还是完成的请求，以及是否包含失败请求。

QPS / TPSQueries / Transactions Per Second

QPS 是每秒查询，TPS 是每秒事务；一次业务事务可能发多个 HTTP 请求和多次 SQL，不能直接等同 RPS。

1 次下单业务 ≠ 1 个请求 ≠ 1 条 SQL计数口径取决于场景与工具定义
想一想：用户打开订单页，一次加载发起 4 个接口请求。假设每秒有 50 次完整页面加载，那么是每秒 50 次业务动作，还是 200 个 HTTP 请求？——答案是前者 50 次、后者 200 个，前提是四个请求都执行。
03 第二组：响应时间与正确性

平均 RT 好看，为什么用户还是抱怨慢？

RT / Latency（响应时间）：一个请求从某个测量起点到终点经历的时间。压测脚本观测的 HTTP 响应时间，和应用内部代码耗时不一定相同；网络与等待边界要讲清。

平均值 Avg

所有样本耗时求平均；少量极慢请求可能被多数快速请求掩盖。

P50 中位数

约 50% 的样本耗时不超过该值，反映“典型请求”。

P95 / P99 尾延迟

P95 表示约 95% 的请求耗时不超过它；P99 看更靠后的慢请求。

前 95 个样本 最慢的 5 个样本 （按耗时排序，示意 P95 的位置）

错误率 Error Rate

失败请求数 ÷ 请求总数。除 HTTP 5xx / 超时，还要检查响应体业务码、空数据和内容错误。某些限流响应需单独归类。

吞吐与饱和 Saturation

吞吐看完成量；饱和看资源或队列是否逼近限制。负载继续增长但完成 RPS 不再增长，常伴随排队与尾延迟恶化。

一组常见观测维度是延迟、流量、错误与饱和度（Google SRE 的“四个黄金信号”）。

04 第三个核心：流量与并发的关系

为什么 200 RPS 不等于 200 并发？

当系统处于相对稳定状态、观测范围一致时，可以用 Little 定律估算平均在途请求数量：

平均在途请求数 ≈ 完成 RPS × 平均响应时间（秒）L = λ × W。前提是稳定系统、同一观测边界、无持续增长的积压
平均在途请求数（教学计算）30

拖动滑块：当 RPS 不变，平均 RT 翻倍，平均在途请求数也会翻倍。

为什么还要注意 Think Time（思考时间）？一个 VU 等响应结束后，还可能停留 2 秒才发下一次请求。假设 100 VU、每次只发 1 个请求、RT=0.2 秒、Think Time=2 秒，理想情况下约 100 ÷ 2.2 ≈ 45.5 RPS，并非 100 RPS。

05 第四个核心：如何产生压力

固定用户数与固定到达速率，测到的东西不同

Closed Model · 闭环模型

固定虚拟用户循环执行。服务器变慢，每轮耗时变长，请求启动速度也可能降低。适合模拟固定用户池行为。

Open Model · 开环模型

按照计划到达速率发请求；先前请求未完成，也可以有新请求进入。适合验证指定到达流量下的承载能力。

关键陷阱：闭环模式可能出现“系统越慢，施压器反而发得越少”，从而低估目标流量下的困难。开环也要监控施压器是否因资源不足而漏发请求（如 k6 的 dropped_iterations）。

常见压测类型

基准 Benchmark / Baseline

低负载记录当前表现，作为比较起点。

负载 Load Test

按目标流量持续验证是否达到业务 SLO。

压力 Stress Test

逐渐超过目标，探索性能转折点与失效方式。

峰值 Spike Test

短时间急剧增压，观察突增冲击及恢复。

耐久 Soak Test

持续长时间，发现慢性泄漏、资源累积。

扩容 Scalability

增加实例或资源，验证吞吐是否有相应提升。

06 第五个核心：系统为什么慢

“RPS 上不去”的背后，可能是排队而非 CPU

简单理解：请求到达速度超过某个环节的持续服务能力时，通常会产生等待。等待时间会扩大 RT；队列满时可能超时、拒绝或失败。只看到一个异常指标，不能直接断定根因。

模型能力上限假设为 240 RPS；只用于理解流量、处理能力和队列关系。

CPU 接近饱和

排查热点计算、序列化、日志、锁竞争；同时看 CPU 使用率、运行队列、线程栈或火焰图。

线程池 / 连接池等待

看活跃数、排队长度、获取连接耗时、超时；CPU 不高也可能因为等待而慢。

数据库慢 SQL

看 SQL 耗时、执行计划、锁等待、连接池、索引和数据库 CPU / IO；不要一开始就加大连接数。

GC / 内存 / 缓存 / 网络

看 GC 暂停、堆占用、缓存命中率、下游超时、重试放大和网络延迟等。跨服务链路尤其要拆开看。

模型约束：上面的响应时间和完成 RPS 是人为设置的教学数值，不是排队论的实际性能预测，也不是连接到真实服务的压测。
07 第六个核心：做一轮靠谱的压测

从需求到复测：一条可执行的工作流

01. 定场景接口、混合比例、真实数据
02. 定门槛目标 RPS、P95、错误率
03. 准备环境隔离、权限、清理方案
04. 逐步施压预热、升压、恒压
05. 分析复测归因、改动、同条件对比

最低限度要有三类证据：发压器指标 + 应用/数据库监控 + 业务正确性检查。仅有一张 JMeter 报表，通常还不能得出可靠的瓶颈结论。

08 最小完整案例：读懂一份压测报告

订单查询接口，到底能稳定扛多少流量？

假设目标：恒定 200 RPS，每阶段稳定压测 20 分钟；成功响应 P95 ≤ 300ms、失败率 ≤ 0.5%，业务结果正确。以下数据全部是教学虚构样本。

100 RPS100120ms0%符合

正确结论：这些假设数据支持“200 RPS 这个测试点满足门槛；300 RPS 不满足”。不代表真实最大能力恰好是 200 RPS；实际阈值可能在两点之间，还要验证稳态、覆盖业务混合流量及长期稳定性。

为什么 300 RPS 目标只完成 270 RPS？可能因为系统拒绝、超时、积压，或施压器根本没有发够预定流量。先核对“计划发出 / 实际到达 / 成功完成 / 失败 / 丢弃迭代”各自数量，再诊断瓶颈。

报告里最容易犯的 4 个错误

  • 只看平均 RT，不看 P95、P99 和失败请求的耗时。
  • 只报最大 RPS，不报持续时长、错误率和响应时间。
  • 只压单接口的小数据集，误当成生产完整业务能力。
  • 把 CPU 高、数据库慢、GC 频繁直接当作“根因”，不做调用链与时序验证。
09 不只看懂术语，试着解释原因

小练习：不看答案，判断现象

问题 1：为什么固定 100 VU，测到的 RPS 可能从 200 降到 100？

查看提示与参考解释

在闭环模型中，只有上一轮完成才开始下一轮。系统响应变慢，每个 VU 每秒能跑的循环更少；即使固定 100 VU，实际 RPS 也可能下降。还应检查脚本的等待时间、错误和施压器资源。

问题 2：200 RPS，平均响应 0.3 秒，稳定情况下平均有几个在途请求？

查看提示与参考解释

根据 Little 定律：平均在途请求数 ≈ 200 × 0.3 = 60。200 是每秒完成请求的速率，60 是同一时刻平均有多少请求未完成。前提是系统稳定、观察边界一致。

问题 3：P95 达标、错误率却升到 4%，能说压测通过吗？

查看提示与参考解释

不能。SLO 是多个约束的组合：速度、错误率、业务正确性、稳定性都要按约定达标。失败可能很快返回，甚至拉低平均 RT；因此失败应单独统计与分析。

下一步怎么学？

先能用自己的话区分 VU、在途并发、RPS、P95；再用上面的 200→300 RPS 案例判断是否达标。确认这些概念后，下一单元才适合动手写 JMeter/k6 测试脚本并部署监控。
