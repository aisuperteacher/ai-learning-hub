主题：如何让多个 AI Coding Agent 并行开发，又不会互相覆盖代码或破坏项目？

系列：AI Coding Agent 工程实战 · 第 2 期｜难度：进阶。 2026 年 11 月 7 日核对 Git、Cursor、Claude Code 和 GitHub 官方文档。昨天讨论 Agent Harness、项目规则、上下文压缩、Hooks 与验收；今天不重复定义这些概念，而是深入学习 多人/多智能体并行编码中的文件隔离、操作权限、精确变更、任务协调和集成验收。

知识点① Git Worktree：独立工作树

1）一句话理解

Git Worktree 让一个 Git 仓库同时拥有多个独立工作目录，每个目录通常检出自己的分支，使不同 Agent 在各自的文件副本上工作。 它不等于重复完整克隆仓库：多个工作树共享底层 Git 对象存储，却拥有各自的工作文件、索引和 HEAD 等状态。

2）为什么需要它？解决什么问题？

传统项目一般只有一份可编辑目录：refund-project/src。Agent A 正在修改 RefundService.java，如果 Agent B 同时切换分支或编辑同一文件，A 的上下文可能失效，甚至发生覆盖。建立三个工作目录以后，A 的改动停留在 refund-agent-bug，B 的改动停留在 refund-agent-tests，主目录不会因两者直接编辑而变化。核心目标是隔离文件修改过程，而不是自动消除最终业务冲突。

3）核心原理和工作机制

先区分三个东西：Git 对象库保存提交、树和文件内容；分支引用指向提交；工作树是磁盘上可以编辑的文件集合。关联工作树共享仓库对象与部分引用，每个工作树有自己检出的文件和独立索引。Git 默认阻止同一个分支同时在两个普通工作树中检出，避免意外覆盖状态。

在 Windows PowerShell 中，在已有且状态明确的 Git 项目运行：

git status --short
git worktree list

git worktree add -b agent/bugfix ../refund-agent-bug HEAD
git worktree add -b agent/tests ../refund-agent-tests HEAD

git worktree list

-b 创建新分支；HEAD 表示以当前提交为起点。成功后进入不同目录即可分别运行 Agent：

Set-Location ../refund-agent-bug
git branch --show-current

此时两个目录可以分别修改同名文件，直到后续集成前都不会直接覆盖对方的物理文件。但多个工作树并非完全独立的 Git 仓库，共享对象和某些 Git 状态仍需小心处理。参见 Git 官方 worktree 手册。

4）贴近日常或软件开发的类比

类似两位工程师编辑同一份设计文档时，各自取得独立工作副本，再在完成后合并差异。不同之处在于 Git Worktree 不只是复制文件夹，它还在同一个版本库上管理关联工作树、分支与提交。类比的边界是：文件隔离不等于语义隔离，不同工作树修改不同文件也可能破坏同一个 API 契约。

5）一个真实 AI 场景示例

Claude Code 在 agent/bugfix 分支修复金额计算，Codex 在 agent/tests 分支新增边界测试。每个 Agent 从对应目录读取与修改文件。Claude Code 官方说明可用 claude --worktree 启动隔离工作树；Cursor 官方 Worktrees 功能介绍在 Agents Window 中隔离不同 Agent，/best-of-n 可以为多个模型尝试创建各自工作树，但并不会自动将获胜结果合并回主工作区。不同产品的 UI/CLI 和版本支持并不统一，标准 Git 命令是跨工具的基础能力。参考 Claude 官方说明、Cursor Worktrees 文档。

6）与易混淆概念的区别

概念 主要用途 不能误认为
Git Branch 指向一条开发提交线 自动创建独立物理工作目录
Git Worktree 独立工作目录与检出状态 进程级安全沙箱
Git Clone 重新创建一份仓库副本 与 Worktree 完全相同的存储和生命周期
Git Stash 暂存未完成的本地修改 长期的并行开发空间
Sandbox 控制进程可访问资源 负责 Git 分支管理

7）实际工作中如何使用

为每项并行任务创建独立分支和 Worktree；分别设置 Agent 的工作目录；启动前先检查 git status --short 与 git worktree list。完成后检查 git -C ../refund-agent-bug status --short 等输出。保存必要成果再移除工作树；Git 默认拒绝 git worktree remove 删除存在未提交修改的工作树。不要为了清理方便随意加 --force。

8）常见误区

误区一：Worktree 是安全沙箱。 它只负责工作目录隔离，不限制进程读取其他路径。误区二：Worktree 之间毫无共享 Git 状态。 关联工作树共享底层对象与部分引用。误区三：分支隔离自动保证合并无冲突。 并不能排除文本或业务逻辑冲突。误区四：直接删除工作目录就是安全清理。 更建议先检查未提交状态，再调用 git worktree remove。

9）思考题

两个 Agent 在两个 Worktree 中都修改了 RefundService.java 的同一个方法。为什么它们开发时可能完全互不干扰，合并后却仍需要解决冲突？

知识点② Sandbox：执行沙箱

1）一句话理解

Sandbox 通过操作系统或受限执行环境控制 Agent 启动的进程可以读写哪些文件、访问哪些网络或执行哪些操作。 它解决的是实际执行权限边界问题，不是 Git 版本控制问题。

2）为什么需要它？解决什么问题？

你给 Agent 一个独立工作目录 C:\Projects\refund-agent-bug，Agent 仍然可能通过 PowerShell 访问主目录、环境变量、SSH 密钥或其他用户可访问文件。当前工作目录只是命令的起点，不是安全边界。 还要考虑不可信仓库脚本、安装依赖执行的生命周期脚本和可能联网的工具命令。

3）核心原理和工作机制

把安全控制拆成三层：工作目录定位决定相对路径在哪里解析；进程沙箱对实际文件系统、网络与进程能力施加限制；审批机制在请求超出当前允许能力时进行确认。逻辑是：模型提出命令 → Harness 根据策略处理请求 → 在沙箱内执行或拒绝 → 必要时审批 → 将真实退出码与输出返回 Agent。自然语言规则可以辅助决策，但不是操作系统访问控制。各 Coding Agent 的策略名称、平台能力与具体拦截条件会不同，不能跨产品套用同一个配置。

4）贴近日常或软件开发的类比

Worktree 是不同工程师各自的办公桌，Sandbox 是进入机房、档案室的门禁。坐在独立办公桌上不代表失去进入其他房间的权限。软件沙箱可在文件路径、系统调用、网络等方面实现技术限制，因此类比不是逐项等价。

5）一个真实 AI 场景示例

用户要求“修复退款接口，不要修改数据库或访问生产环境”。比较稳妥的组合是：独立 Worktree + 限制访问所需目录 + 不把生产凭据放在测试环境 + 在高风险操作前审批 + 审查实际工具日志。运行 mvn test 也必须确认测试脚本是否涉及外部数据库、容器或网络；仅凭名称不能证明其安全性。

6）与易混淆概念的区别

概念 主要约束
项目规则文件 以自然语言说明行为约定
Worktree 代码工作目录、分支与修改状态
Sandbox 实际进程资源与操作能力
审批策略 指定哪些操作需授权
容器 隔离部署/运行环境的技术之一，安全性依赖具体配置
最小权限 仅授予完成目标所需的访问能力

7）实际工作中如何使用

在 Windows 上运行实验性 Agent 时使用最小权限账户和可信目录，避免默认管理员权限；隔离生产凭据；把构建和测试放到适当环境；评估沙箱对目录写入和网络的真实限制。在使用 Codex、Claude Code、Pi 或 Cursor 的内置安全能力时，以各工具当日实际官方文档和运行设置为准，不虚构统一的 sandbox_mode 或审批开关。

8）常见误区

误区一：独立工作树就是执行沙箱。 错，两者对象不同。误区二：只有写文件才危险。 读取秘密与外传也可能有风险。误区三：自动批准不增加风险。 错，它扩大了免确认操作的范围。误区四：测试命令一律可信。 错，测试与构建过程可执行任意脚本，必须理解项目实际行为。

9）思考题

你创建了独立 Worktree，但 Agent 仍能读取 C:\Users\...\.ssh 中的密钥。当前具备什么能力、缺少什么能力？为什么只在提示词里说“不要读取密钥”不够？

知识点③ Patch：代码补丁

1）一句话理解

Patch 用结构化差异文本记录原文件哪些内容被删除、哪些新内容被增加，可以审查修改，也可以在条件满足时应用到另一份工作树。 它把“Agent 改了文件”变成可明确检查的修改记录。

2）为什么需要它？解决什么问题？

Agent A 改了服务逻辑，Agent B 补充测试。直接复制整个目录可能覆盖正确代码，且难以确定到底改变了什么。Patch 只描述差异，可以帮助限定范围、代码审查和迁移必要修改。

3）核心原理和工作机制

统一差异格式使用 --- 表示旧路径、+++ 表示新路径、@@ 表示差异块，行首 - 为移除、+ 为新增：

--- a/RefundService.java
+++ b/RefundService.java
@@ -1,3 +1,4 @@
 public Refund findById(String id) {
-    return repository.findById(id).get();
+    return repository.findById(id)
+        .orElseThrow(() -> new RefundNotFoundException(id));
 }

在相关工作树执行 git diff --stat、git diff --check、git diff，观察改变了哪些文件、是否存在部分补丁格式问题、具体文本内容。必要时将未暂存差异输出为文件：git diff > ../refund-fix.patch。目标工作树中先运行 git apply --check ../refund-fix.patch 检查是否可应用，确认安全以后才执行 git apply ../refund-fix.patch。Git 官方文档明确：--check 只检查，不应用补丁；正常 git apply 修改目标文件，但不自动创建提交。参见 Git apply 手册。

4）贴近日常或软件开发的类比

类似 Word 的修订标记：可以看到删除了什么、新增了什么。不同之处在于 Git Patch 表示文本与上下文差异，不能推断修改在业务层是否合理。两个 Patch 不发生文本冲突，不代表实现逻辑兼容。

5）一个真实 AI 场景示例

Agent A 修复 RefundService 的未找到订单异常；你希望把这一项修复带入集成分支，而非复制 Agent A 的整个目录。先审查 git diff 是否只修改必要文件，检查补丁适用性，再选择是否应用或采用提交级的合并方式。注意：git diff 默认不显示未跟踪文件内容，也不等同于所有历史提交的总差异；应结合 git status、暂存区和提交状态判断。

6）与易混淆概念的区别

概念 区别
Diff 两个状态的差异表示
Patch 可审查和应用的差异文本
Commit Git 的持久历史快照及元数据
Cherry-pick 将特定提交引入当前分支
Merge 合并不同历史与改动
复制文件 复制最终内容，不表达差异和修改上下文

7）实际工作中如何使用

将补丁审查设为 Agent 交付步骤。先查看实际变更文件、修改块，再核对任务授权范围，防止 Agent 意外更改数据库配置、敏感资料或不相关模块。git diff --check 是格式层面检查，不是编译或业务逻辑验证。对于新增未跟踪文件，可以使用 git status --short 检查，必要时明确暂存或在独立提交中管理。

8）常见误区

误区一：能应用 Patch 就代表正确。 只表示格式及上下文匹配。误区二：git diff 总是涵盖全部改动。 未跟踪和已提交内容需要分别处理。误区三：Patch 不会修改工作树。 git apply 会实际写文件。误区四：没有文本冲突就是语义兼容。 不同文件中的单位、字段和协议不一致仍然可能导致错误。

9）思考题

Agent A 将金额单位从元改为分，Agent B 在独立测试文件中继续使用元。为什么 Git 可能没有文本冲突，合并后的退款逻辑却错误？

知识点④ 并行任务拆分与冲突控制

1）一句话理解

并行任务拆分是根据文件范围、接口依赖、业务约束和验收标准，把大任务拆成能相对独立完成并最终集成的子任务。 关键不是开多少 Agent，而是能否减少无效协调与返工。

2）为什么需要它？解决什么问题？

三个 Agent 都修改同一退款服务的全部内容，可能产生三份互相不兼容的实现。即使每个都能完成，集成成本仍可能抵消并行收益。需要识别哪些任务独立、哪些任务有前置依赖。

3）核心原理和工作机制

可从三个维度判定：文件重叠度（是否编辑同一位置）、接口依赖度（一个结果是否决定另一个结果）、验证独立性（能否独立证明完成）。粗略耗时模型：

[T_{parallel}\approx\max(T_A,T_B,T_C)+T_{integration}+T_{verification}]

这是帮助判断的工程模型，不是固定预测公式；实际还可能有沟通、资源争用和失败重试开销。比如 A 修复服务层逻辑，B 设计边界测试，C 整理文档可以部分并行，但 B 和 C 仍要对齐 A 的最终接口与行为。

4）贴近日常或软件开发的类比

类似前端、后端与测试团队并行开发。先确定接口契约，才能在分开工作时降低返工。Agent 可能更容易在上下文不足时自作假设，因此任务契约应明确允许修改的范围、预期输出、输入依赖及停止条件。

5）一个真实 AI 场景示例

Agent 任务 允许修改 验收
A 修复 RefundService 异常处理 服务层相关文件 服务层测试通过
B 增加退款边界测试 测试目录 关键边界覆盖且测试可执行
C 更新退款 API 文档 文档目录 与集成后的接口一致

如果 B 的断言依赖 A 尚未决定的异常类型，则应先冻结约定，或先做测试设计、等 A 完成再落实到最终测试代码。C 的文档也需要在合并后复核。

6）与易混淆概念的区别

概念 主要作用
任务拆分 将目标分成可执行子问题
子智能体 在主任务内进一步调用角色或执行单元
Worktree 隔离文件编辑状态
协作消息 交换必要的接口和状态
集成 整合各任务的最终产物
同题竞争 多个 Agent 尝试相同任务再选更好的方案

7）实际工作中如何使用

给每个 Agent 一份明确契约：任务目标、允许目录、禁止操作、依赖的接口约定、输出产物、独立测试、集成验收。高度耦合的核心业务先做接口确认，再让其他部分并行；完全独立的文档整理或调查工作可以更早启动。

8）常见误区

误区一：Agent 数量翻倍速度就翻倍。 协调和集成成本会增加。误区二：改不同文件就绝对独立。 仍可有协议依赖。误区三：各自称完成就等于整体完成。 需要组合验证。误区四：所有任务均应并行。 存在显著前置依赖时，分阶段串行更稳妥。

9）思考题

Agent A 修改 REST API 返回结构，B 根据该结构编写集成测试，C 更新 OpenAPI。哪些工作可立即并行，哪些必须在接口约定稳定后完成？

知识点⑤ 合并验证与质量门禁

1）一句话理解

合并验证与质量门禁是在不同 Agent 的结果进入共同代码线之前及之后，通过差异审查、自动测试和仓库规则检查实际集成结果。 成功标准不是多个 Agent 都说完成，而是可核验的整体行为。

2）为什么需要它？解决什么问题？

A 和 B 在各自工作树上测试都通过，合并后仍可能因为接口变更、配置差异、同名类、依赖版本或缺少跨模块测试而失败。局部正确不推出整体正确，因此需要在组合状态重新测试。

3）核心原理和工作机制

建议流程：查看两个 Agent 的变更范围 → 审查补丁与提交 → 在候选集成分支合并 → 跑相关完整测试 → 检查业务约束与接口兼容性 → 人工或自动审查 → 确认满足条件后再合并正式目标分支。GitHub 官方支持分支保护、必要状态检查、PR 审查，以及适合高频合并的 Merge Queue；只有真实配置到仓库后，它们才具有约束效果。Merge Queue 可以在候选组合变更上重新运行要求的检查。参考 GitHub 官方保护分支说明。

4）贴近日常或软件开发的类比

汽车生产中，发动机和变速箱各自测试合格，不等于整车装配后必然正常。组件测试确保局部行为，集成测试验证组合协作；软件集成还需要关注业务接口和非功能约束。

5）一个真实 AI 场景示例

A 修正退款金额算法，B 更新边界测试。集成后要确认金额单位和小数精度、已有 API 兼容、异常行为、所有新增测试、无关模块变更和敏感信息。可在安全且适当的 Maven 项目运行：

git status --short
git diff --check
.\mvnw.cmd test

如果项目没有 Wrapper 且已安装 Maven，可以使用 mvn test。这些命令没有在用户项目实际执行；还需要检查测试脚本是否连接外部系统或执行有副作用的操作。

6）与易混淆概念的区别

概念 关键作用
Git Merge 整合代码历史和文件修改
文本冲突检查 判断 Git 能否组合修改块
单元测试 验证局部行为
集成测试 验证组件协作
代码审查 关注设计、安全和维护性
质量门禁 未满足条件时阻止进入目标分支

7）实际工作中如何使用

建议设置三道门：改动范围门禁（是否越界修改或泄漏敏感内容）；自动验证门禁（测试、构建、静态分析，记录真实退出状态）；集成审批门禁（合并前检查风险、必要审查）。GitHub 仓库可依业务风险启用必需检查和 PR 审核，并确认检查状态源可信。不要把工具的最终自然语言汇报当成测试证据。

8）常见误区

误区一：没合并冲突就等于兼容。 业务冲突可能无文本痕迹。误区二：分别测试通过就不用重测。 必须看集成状态。误区三：测试通过就不用审查。 覆盖可能不足。误区四：门禁越多越好。 需要平衡风险与反馈成本。

9）思考题

两个 Agent 独立通过测试，合并后金额计算异常。你如何排查接口契约、业务单位、数据边界和测试覆盖，并构造稳定复现的测试？

今日串联：安全的多 Agent 开发知识链

五项能力应被串联，而不是互相替代：

用户任务 / 确定约束
       │
       ▼
④ 任务拆分：明确接口契约和允许改动范围
       │
       ▼
① Worktree：独立目录、独立任务分支
       │
       ▼
② Sandbox：限制真实执行权限与访问范围
       │
       ▼
③ Patch：记录、审查、迁移准确修改
       │
       ▼
⑤ 质量门禁：集成后运行测试、审查并决定合并

这只是逻辑关系图：沙箱贯穿实际进程运行，补丁审查和测试可以在开发中多次执行。Worktree 解决工作文件干扰；Sandbox 解决执行权限；Patch 解决差异审查；任务拆分解决协作依赖；质量门禁解决最终交付是否可信。

今日微型练习：Windows PowerShell 两个独立工作树

预计 30—45 分钟。目标： 无需付费 API、无需真实 Agent，通过标准 Git 体验两个独立工作目录的修改隔离，理解未跟踪文件与补丁，并提出安全集成方案。

第一步：准备全新教学仓库

在 PowerShell 中执行以下命令，所有操作都限定在系统临时目录中的独立练习项目，不指向实际生产仓库：

$root = Join-Path $env:TEMP 'agent-worktree-lab'
New-Item -ItemType Directory -Force $root | Out-Null
Set-Location $root
git init -b main
'refund.limit=5000' | Set-Content -Encoding utf8 policy.txt
git add policy.txt
git -c user.name='Lab User' `
    -c user.email='lab@example.invalid' `
    commit -m 'Initial lab state'

预期： 建立一个初始提交，policy.txt 保存基准值。风险检查： 如果临时目录已存在同名实验仓库，应先检查原有文件，不要覆盖未保存成果。旧版 Git 如果不支持 git init -b main，可以先运行 git init，再按版本支持的命令命名分支。

第二步：创建两个 Worktree

git worktree add -b agent/bug ../agent-lab-bug HEAD
git worktree add -b agent/docs ../agent-lab-docs HEAD
git worktree list

预期： 列出主工作树和两个独立目录。故障排查： 检查目标目录、分支名称和 Git 状态，避免对已有工作树加 --force。

第三步：两个工作目录分别修改

Set-Location ../agent-lab-bug
'refund.limit=6000' | Set-Content -Encoding utf8 policy.txt
git diff

Set-Location ../agent-lab-docs
'refund policy documentation' | Set-Content -Encoding utf8 README.md
git status --short

预期： A 改了已跟踪的 policy.txt，B 新增一个未跟踪的 README.md，两边不直接覆盖文件。B 的新文件默认不一定显示在 git diff 中，可用 git status --short 查看。

第四步：从主工作树验证隔离

Set-Location ../agent-worktree-lab
git status --short
git -C ../agent-lab-bug diff --check
git -C ../agent-lab-docs status --short
git worktree list

预期： 主工作树保持原始提交状态；两个关联工作树分别保留独立修改。风险检查： 不要在任何关联工作树仍有未保存工作时随意重置分支或删除目录。

第五步：审查 Patch

Set-Location ../agent-lab-bug
git diff --stat
git diff --check
git diff

预期： 能看到 refund.limit=5000 变为 refund.limit=6000。解释为什么这是内容差异，不等于业务规则合理。故障检查： 若 git diff 为空，先确认工作目录、文件是否被跟踪、改动是否已经暂存或提交。

第六步：设计集成前验收

写一份简单检查单：A 改了什么、是否越界、是否有单元测试；B 新增什么、是否受 Git 管理、文档与最终代码是否一致；两项工作是否有接口依赖；集成后必须运行什么测试。预期成果： 能明确区分每个 Agent 独立完成和整体任务完成。

第七步：安全清理（可选）

先检查是否需要保留成果，如果需要就提交到实验分支或保存补丁，不要直接强制删除。运行：

Set-Location ../agent-worktree-lab
git worktree list
# 仅当关联目录干净且成果已保存时：
git worktree remove ../agent-lab-bug
git worktree remove ../agent-lab-docs

如果出现未提交文件提示，不要加 --force，先检查内容，再决定是否保留或撤销。这次练习不要求合并正式分支，也不要求实际删除实验成果。

验收标准

检查点 合格证据
工作树隔离 git worktree list 显示三处目录
分支理解 知道 Branch 与 Worktree 不同
安全边界 能说清工作区隔离不等于进程沙箱
差异审查 能用 git diff 看到 A 的修改
新文件认知 能用 git status 看到 B 的未跟踪文件
任务拆分 写明 Agent A/B 允许修改的范围
集成验证 解释为什么合并后还要重测
清理安全 不用强制方式丢弃未保存成果

预期结果与综合思考

练习通过时，你应能展示三个工作目录、不同的修改状态、准确的 Diff 和一份集成前验收清单。若某一步失败，先检查工作目录路径、分支是否已存在、文件跟踪状态和命令退出信息，不应编造成功日志。

综合问题： 如果你准备让 Codex 和 Claude Code 在同一个 Spring Boot 项目里分别修复退款业务与编写集成测试，你会怎样安排两个 Worktree、接口契约、执行权限及最终集成测试？

最终结论：多 Agent 同时运行不天然等于高效率；可靠的并行开发依赖工作目录隔离、真实执行权限边界、明确任务契约、可审查差异以及集成后的独立验证。
