Chapter 01 / Five concepts

1. Agent Harness——智能体运行框架

Agent HarnessIPA：/ˈeɪ.dʒənt ˈhɑːr.nɪs/近似发音：诶真特 · 哈尔尼斯中文含义：智能体运行框架

1. 一句话理解

Agent Harness 是围绕大模型建立的一套运行系统，负责管理工具、工作环境、执行循环、会话状态、权限和结果反馈，让模型能够持续完成实际任务。

模型负责提出判断与行动，Harness 负责提供行动能力、实际执行条件和运行控制。模型可以建议修改 Java 文件，但读取、应用补丁、执行测试和处理失败都需要运行环境协调。

2. 为什么需要它／解决什么问题

假设任务是“修复退款查询接口空指针，补充测试，不要改数据库”。普通聊天模型可能只生成代码。Coding Agent 则要定位仓库、阅读相关类与测试、分析错误、修改文件、运行构建、检查变更和失败恢复。没有 Harness，开发者需手动复制模型输出、运行命令、再回传结果。Harness 把模型的建议转化成受控、持续、可观察的执行过程。

3. 核心原理和工作机制

典型循环：

用户目标 + 项目规则
  ↓
Harness 装配上下文、会话与权限
  ↓
模型决定下一步：读？搜？改？测？
  ↓
Harness 校验和执行工具调用
  ↓
工具返回成功 / 失败 / 超时 / 拒绝
  ↓
把结果交给模型 → 决定继续或结束

模型提出工具调用 ≠ 工具已经成功执行。 参数可能无效、权限可能被拒绝、文件可能不存在、测试可能失败。运行环境需反馈实际状态。DeepSeek Harness 官方将模型、工具、技能、会话、沙箱、存储、循环、调度和 UI 等拆成可组合插件，采用 Cordis 架构；Pi 也提供工具注册和事件扩展能力。

4. 贴近日常或软件开发的类比

把模型比作能分析问题的工程师，Harness 比作工程师工作的基础环境：终端、编辑器、Git、测试工具、权限、运行记录。工程师在纸上写完方案不代表系统已经修复。边界： Harness 不只是安装工具，还要处理模型调用、结果反馈和状态；它不能天然保证工程师或模型判断正确。

5. 一个真实 AI 场景示例

在 Spring Boot 仓库修复 /refunds/{id} 查询异常：

读取 RefundController.java
  ↓ 读取 RefundService.java
  ↓ 查找相关测试
  ↓ 应用最小代码修改
  ↓ 执行 Maven Test
  ↓ 检查 Git Diff
  ↓ 汇报已验证 / 未验证 / 失败

测试失败时，Harness 把退出状态和错误输出反馈给模型；模型可决定继续修复。但重试次数、改动范围和执行授权应受约束。

6. 与易混淆概念的区别

概念 核心职责
大模型 理解、推理、行动建议
Tool Calling 表达希望调用哪个工具及参数
Harness 协调工具、执行循环、会话和权限
MCP 标准化连接工具与外部服务
Skills 可复用任务流程与知识材料
Agent SDK 辅助集成或构建智能体

Harness 是运行系统，不是一种新模型。同一模型在不同智能体中表现不同，可能是工具、上下文、权限和验证能力不同。

7. 实际工作中如何使用

比较 Coding Agent 时，不只看模型榜单。要检查：能否正确读取/编辑代码；失败是否可恢复；是否有运行轨迹；是否支持权限与沙箱；如何扩展工具和流程；是否能独立核验交付。选择一项低风险 Java/Maven 任务，在两个 Agent 上使用同样输入和验收标准，比较测试结果、修改范围、耗时与真实成本。

8. 常见误区

① 模型强就不需要 Harness？ 不对，环境和工具状态仍要管理。

② 所有 Coding Agent 仅 UI 不同？ 不对，扩展与执行机制可能不同。

③ Agent 说“已完成”就等于验证过？ 不对，要查真实工具记录与产物。

④ Harness 越复杂越好？ 不一定，简单可测试的任务可用更轻的运行框架。

9. 一个思考题

两个 Agent 使用相同模型，却对同一 Java 项目给出不同修复结果，你应先检查模型参数，还是工具、上下文和验证方式？怎样制定公平的对照条件？

Chapter 02 / Five concepts

2. 项目级规则与指令装配——让 Agent 理解仓库规范

1. 一句话理解

项目级规则把仓库架构约定、执行命令、禁止事项和验收要求，以可复用方式提供给 Coding Agent。 让模型每次开始任务都能获得准确、相关的工作边界，而非靠聊天历史猜测。

2. 为什么需要它／解决什么问题

模型可能知道 Spring Boot 通用最佳实践，却不知道当前仓库的特殊限制：Controller 不得访问数据库、禁止未经授权改迁移脚本、变更行为后必须测、不得自动提交。没有这些规则，Agent 可能虽写出能运行的代码，却破坏项目风格和边界。

3. 核心原理和工作机制

项目规则通过仓库文件或工具配置进入 Agent 的上下文，作用域与优先级由产品实现决定。官方文档确认：

工具 可用入口示例
Codex AGENTS.md，支持按目录作用域
Claude Code CLAUDE.md 和规则文件，文档也说明 AGENTS.md 相关支持
Cursor .cursor/rules/*.mdc，也支持 AGENTS.md
Pi 项目配置、Skills、Extensions 等机制

不要假定文件名、扫描路径或覆盖优先级跨工具完全相同。 长期项目约束与一次性任务提示应分开。

4. 贴近日常或软件开发的类比

新工程师入职要看仓库 README、架构约定和代码规范。项目规则就像持续可用的入职指南。边界： 自然语言规则可能被模型误解或遗漏；对重要安全限制，还必须有实际权限、沙箱和测试。

5. 一个真实 AI 场景示例

在 Maven/Spring Boot 仓库根目录，为支持该文件的工具准备：

# Repository Guide
## Architecture
- Keep controller, service and repository responsibilities separate.
- Prefer minimal changes over unrelated refactoring.
- Preserve public API behavior unless requested.
## Verification
- Add or update tests when changing behavior.
- Run Maven tests before reporting success.
- Review Git diff for unrelated modifications.
## Boundaries
- Do not edit database migrations unless requested.
- Do not commit or push without explicit authorization.
- Never place credentials in source files.

当前任务另写：“仅修复退款查询空指针；不改数据库，不重构其他模块；完成后运行相关测试并报告文件”。任务与规则的职责不同。

6. 与易混淆概念的区别

概念 解决的问题
项目级规则 仓库长期遵守什么
当前任务提示词 本次具体要做什么
Skill 某类任务按什么步骤完成
Hook 某事件发生时自动做什么
权限配置 真正允许执行哪些操作

不要把全部信息塞进一个巨大的 AGENTS.md。 OpenAI 的相关开发者文章也提醒，冗长重复的项目规则和 Skills 会增加上下文负担。

7. 实际工作中如何使用

分成三层：①仓库通用规则（架构、命令、安全）；②目录专属规则（如支付模块不同于工具模块）；③当前任务（目标、允许改动范围和验收）。真正修改前，先让 Agent 复述已读取的规则、准备改哪些文件、准备执行什么测试。用可观察的行为检验，而不是以为写入文件后就必然被使用。

8. 常见误区

① 规则越长越可靠？ 不一定，容易冲突或稀释重点。

② 写进仓库所有 Agent 都会自动读取？ 不对，要核实扫描机制。

③ 自然语言规则可以替代系统权限？ 不对。

④ 每个任务都要复制完整架构文档？ 不一定，优先提供与本次工作有关的信息。

9. 一个思考题

项目规则说不得修改数据库迁移脚本，但当前用户明确要求新增迁移脚本。Agent 应如何处理冲突？哪些情况下应先确认授权与变更范围？

Chapter 03 / Five concepts

3. Context Compaction——上下文压缩

Context CompactionIPA：/ˈkɑːn.tekst kəmˈpæk.ʃən/近似发音：康泰克斯特 · 肯派克申中文含义：上下文压缩

1. 一句话理解

上下文压缩是在长任务中，将较早的交互与工具记录总结成较短的任务状态，以释放有限的模型上下文空间。 它是有信息取舍的摘要，不是无损打包。

2. 为什么需要它／解决什么问题

Coding Agent 持续累积需求、规则、源代码、工具输出、失败日志、修改记录等。若模型上下文容量有限，全部原样放入会增加成本，最终可能超出容量。压缩要优先留下用户目标、不可突破的限制、实际文件状态、已验证结果和待办，而不是重复日志。

3. 核心原理和工作机制

逻辑流程：

长会话 → 监控上下文容量 → 达到阈值
  ↓
识别：用户约束/文件修改/测试结果/失败原因/下一步
  ↓
生成结构化摘要 + 保留必要近期记录
  ↓
继续 Agent 下一轮执行

Pi 官方文档说明可自动压缩或使用 /compact；一个典型触发条件是 contextTokens > contextWindow - reserveTokens。Pi 的设置涉及 reserveTokens、keepRecentTokens，但阈值和摘要方式不能套用到所有产品。

压缩风险：第 1 轮用户规定“不能改数据库”，第 35 轮摘要却只写“正在修复数据库相关问题”，后续模型就可能忽略原始边界。

4. 贴近日常或软件开发的类比

像团队交接摘要：第二天接手的工程师不必读完所有聊天，但必须知道任务目标、已决定事项、不能做什么、当前版本和下一步。边界： 摘要不能替代原始日志；关键细节可能丢失。

5. 一个真实 AI 场景示例

运行到一半的退款接口任务，可以用以下交接摘要：

目标：修复退款查询空指针。
禁止：改数据库、提交或推送。
已修改：RefundService.java、RefundServiceTest.java。
已验证：初次测试失败，定位到 Mock 配置。
待完成：重新执行 Maven 测试、检查 git diff。
当前结论：最终修复尚未验证成功。

摘要不能把“计划测试”写成“测试通过”，也不能把假设根因当成已确认事实。

6. 与易混淆概念的区别

机制 与压缩的区别
清空会话 移除历史，不保证保留状态
长期记忆 在会话外保存持久信息
RAG 根据需要检索外部资料
Prompt Cache 复用满足条件的模型输入计算
Git Commit 保存代码版本而不是摘要

上下文压缩不能代替 Git、测试报告或权威的项目规则。

7. 实际工作中如何使用

把长期约束放在项目规则；把本次任务写成清晰提示；用 Git 表示真实文件状态；用测试输出记录实际结果；用压缩摘要跟踪进度。压缩后可以要求 Agent 复述禁止事项、已完成的验证和未完成任务；如果摘要冲突，以真实仓库与可信记录复核。

8. 常见误区

① 压缩是无损的？ 不对。

② 上下文窗口大就不需要压缩？ 长时间任务仍可能需要。

③ 压缩后仍记得所有原始细节？ 取决于保留机制。

④ 记住文件名就能恢复代码状态？ 不对，必须读取工作区或 Git。

9. 一个思考题

一个运行两小时的 Agent 只能保留 1000 Token 摘要，你优先保留完整测试日志，还是用户硬约束、实际变更、测试结论和未完成事项？什么情况下必须另外保存原始日志？

Chapter 04 / Five concepts

4. Hooks——事件钩子

HooksIPA：/hʊks/近似发音：胡克斯中文含义：事件钩子

1. 一句话理解

Hooks 是在 Coding Agent 的某个生命周期事件发生时，自动执行自定义处理逻辑的扩展机制。 例如运行 Shell 前检查、修改文件后格式校验或收集工具执行指标。

2. 为什么需要它／解决什么问题

即使项目规则写了“每次修改后检查格式”，长任务中的模型也可能遗漏。Hook 能在对应事件触发固定程序，但具体能否阻止、修改还是只记录，取决于产品和事件。它使一部分重复检查不依赖模型每次主动记起。

3. 核心原理和工作机制

通用事件链：

Agent 准备行动
  ↓
Harness 发布生命周期事件
  ↓
匹配 Hook → 运行自定义处理
  ↓
记录 / 允许 / 按支持的语义阻止 / 补充上下文
  ↓
继续执行流程

官方资料分别说明：Claude Code 提供 PreToolUse 等事件；Cursor 有 .cursor/hooks.json、beforeShellExecution、afterFileEdit 等；Pi 的 TypeScript Extensions 可订阅事件、注册工具并执行部分拦截。Pi 扩展在本机 Pi 进程内运行，拥有对应系统权限，应只安装可信扩展。

4. 贴近日常或软件开发的类比

像软件系统的事件监听器或拦截器：某个 HTTP 请求到来时执行检查，某个文件修改完成时触发格式校验。边界： 具体 Agent Hook 的事件格式、失败语义和权限与 Spring 拦截器不同，不能照搬。

5. 一个真实 AI 场景示例

Cursor 官方文档支持项目级 .cursor/hooks.json 与 afterFileEdit 事件，教学配置示例：

{
  "version": 1,
  "hooks": {
    "afterFileEdit": [
      {"command": "python .cursor/hooks/check_edit.py"}
    ]
  }
}

check_edit.py 需要自己实现，不是内置文件；它可以接收事件输入，记录修改或执行检查。编辑后的 Hook 不能替代修改前拦截。 阻止高风险动作需采用当前工具支持的前置事件和真实权限机制。

6. 与易混淆概念的区别

概念 核心职责
规则 告诉 Agent 应遵守什么
Skill 告诉 Agent 某类任务如何做
Hook 在某个事件自动做什么
MCP 连接外部工具/服务
Plugin 打包与扩展一组能力
沙箱/权限 从系统层面约束实际操作

例如 Skill 给出代码审查流程，Hook 可以在提交前或文件编辑后触发对应检查，沙箱限制可写范围。

7. 实际工作中如何使用

优先三个低风险用途：①文件编辑后执行格式检查；②收集工具调用的命令、退出码与耗时；③在支持阻止语义的前置事件中对敏感操作触发确认。应为 Hook 设置适当超时、可诊断日志和失败策略。在 Windows 上要核对解释器、PowerShell/Git Bash、工作目录与路径。安全仍需靠系统权限和最小授权，不能只依赖字符串匹配。

8. 常见误区

① Hook 等于 Skill？ 不对。

② 加一个 Hook 就绝对安全？ 不对，脚本和环境也可能失败。

③ 所有 Agent 使用同一配置格式？ 不对。

④ Hook 越多越好？ 不一定，可能增加延迟与维护成本。

9. 一个思考题

你希望 Agent 每次执行数据库写命令前经过人工确认，应该组合项目规则、前置 Hook 与数据库账户权限中的哪些机制？为什么不能仅依赖 Hook 的关键词匹配？

Chapter 05 / Five concepts

5. 可验证的任务闭环——从“AI 说完成”到证据证明完成

1. 一句话理解

可验证的任务闭环就是预先约定完成标准，用真实文件、测试、差异和运行记录判断 Agent 是否真的完成任务。 自然语言的“已修复”并非充分的工程证据。

2. 为什么需要它／解决什么问题

Agent 可能改错文件、编译通过但业务测试失败、擅自改数据库脚本、没有执行测试却说已完成，或工具报错后总结仍显得成功。需要把模型自述与真正的系统状态分开，防止误上线。

3. 核心原理和工作机制

典型五阶段：

目标与验收条件
  ↓ 定位问题与确认范围
  ↓ 实施最小修改
  ↓ 实测 + Diff 检查
  ↓ 依据证据决定完成 / 继续修复 / 请求帮助

分别检查：①代码是否真的改了；②测试是否真的运行且结果如何；③是否符合业务行为与禁止事项。例如：退款记录不存在应返回规范 404；现有订单仍正常；数据库迁移未变；相关测试真实通过。未运行必须标记未验证。

4. 贴近日常或软件开发的类比

像软件交付和测试验收：开发人员觉得 Bug 修了，需要测试与代码审查复核。边界： 自动测试也可能不完备，测试通过不代表所有真实场景安全。

5. 一个真实 AI 场景示例

理想交付报告（教学示例，不是真实执行日志）：

目标：修复退款查询空指针。
修改：RefundService.java、RefundServiceTest.java。
验证：Maven 单元测试通过；已检查 Git Diff。
约束：数据库迁移未修改。
未验证：生产请求和外部依赖联调。
剩余风险：需测试环境集成验证。

如果实际 mvn test 失败，则必须汇报失败。不能套用示例里的“通过”。

6. 与易混淆概念的区别

方式 功能
模型自我检查 再次审阅自己的输出
单元测试 验证局部程序行为
集成测试 验证跨模块协作
Git Diff 显示源代码修改
代码审查 审核设计、质量和风险
任务验收 判断最终是否达到用户目标

自我检查不能替代真实执行测试；测试通过也不等于获得生产发布批准。

7. 实际工作中如何使用

Windows PowerShell 中，可在可信的 Git/Maven 项目内执行：

git status --short
git diff --check
git diff
.\mvnw.cmd test

若没有 Maven Wrapper，而已安装 Maven，可改为 mvn test。运行前了解测试是否触发外部副作用。必须核对退出状态、测试报告和文件差异。git diff --check 主要检查补丁格式，不是代码正确性证明。

8. 常见误区

① Agent 最终回答就是任务完成？ 不对。

② git diff --check 通过说明代码逻辑正确？ 不对。

③ 单元测试通过就可以直接上线？ 不对。

④ 有完整运行轨迹就不需要测试？ 不对，轨迹是过程证据，测试验证行为。

9. 一个思考题

Agent 修复 Java Bug，测试通过，但 Git Diff 出现三个与任务无关的重构；用户只要求最小修复。你认为任务完成了吗？应该如何判断需要回退哪些修改？

今日串联：五个知识点构成怎样的 Coding Agent 工程链？

用户提出：使用 Coding Agent 修复 Spring Boot 退款查询 Bug，保持接口兼容，补充测试，不改数据库、不自动提交。

① Agent Harness
接收任务、管理模型、工具与状态
        ↓
② 项目级规则与指令装配
提供仓库规范和本次操作边界
        ↓
③ Context Compaction
长会话中保留关键约束、实际状态和未完成事项
        ↓
④ Hooks
在适当生命周期事件中自动执行预设检查
        ↓
⑤ 可验证任务闭环
检查实际 Diff、测试结果、交付和剩余风险

这是职责链，并非严格时间顺序。 Harness 贯穿全程；项目规则持续发挥约束作用；压缩按需要触发；Hooks 可在多个事件触发；验证可能重复多轮。

核心结论：优秀的 Coding Agent = 有能力的模型 + 合理的 Harness + 准确的项目上下文 + 受控工具执行 + 可验证结果。

今日微型练习：验证一个 Coding Agent 的真实工作质量

建议用时：30～45 分钟。 使用已安装的 Pi、Claude Code、Codex 或 Cursor 中的任意一个，在可信、无敏感信息的练习仓库里完成低风险代码修复。不需要安装或购买新工具。

第一步：准备实验仓库

使用独立分支或独立工作区，执行：

git status --short
git branch --show-current

如果存在未提交的个人修改，先确认归属；不允许 Agent 擅自清理或覆盖。

第二步：准备项目规则

在当前产品支持的项目规则入口放入以下内容，注意不同工具不一定读取相同文件名：

# Coding Agent Practice Rules
- Make only changes required for the current task.
- Do not modify database migrations.
- Do not commit or push automatically.
- Run relevant tests before reporting success.
- Report changed files and verification evidence.

Claude Code、Codex、Cursor 的具体文件位置和作用域，使用本文附带的官方文档核对。

第三步：提交明确任务

请先读取本项目适用的 Agent 规则，并说明你理解的边界。目标：选择一个已有测试覆盖的低风险空值处理问题，只进行最小必要修复；如果找不到合适练习问题，先提出方案，不要自行扩大范围。禁止：改数据库迁移、删除文件、提交或推送。先定位问题和拟改动文件，再修复，运行相关测试，检查 Git Diff。最终报告必须区分：已运行并通过、运行失败、因环境限制未验证。

第四步：观察 Harness 轨迹

按以下表格记录，不要只读最终回复：

检查项 要观察的事实
项目规则 是否真正读取且遵守
工具调用 是否定位并读取相关文件
修改行为 是否仅改任务相关文件
执行结果 是否真的运行测试
失败恢复 是否说明错误并按边界尝试修复
最终报告 是否区分完成、失败、未验证

第五步：模拟上下文恢复

任务执行若干轮后，请 Agent 生成如下摘要：当前目标、禁止事项、已修改文件、已验证测试、未解决问题、下一步动作。检查是否保留初始硬性限制。该练习是人工模拟交接，不需要刻意耗尽上下文。

第六步：独立手动验收

在可信仓库里执行：

git status --short
git diff --check
git diff
# 若 Maven Wrapper 已存在
.\mvnw.cmd test
# 否则，可在安装 Maven 后运行：mvn test

先了解测试是否会访问外部系统或触发业务副作用。核对测试退出状态、文件差异与 Agent 总结是否一致。

第七步：改变一个条件

重新运行同类任务，但加上：本次只允许修改测试文件，不允许修改生产代码。观察 Agent 是否识别潜在冲突并请求确认，而不是自行突破约束。
