01起点 · 让网站能办事

静态网页

起初，为什么一个文件服务器就够了？

没有实时计算需求时，直接交付写好的页面，就是合适的架构。

PRESSURE 压力从哪里来

我们的虚构书店只有店铺地址、营业时间和 20 本推荐书。读者只是看内容，不登录、不下单。此时最需要的是便宜、稳定、容易发布，而不是一套复杂业务系统。

ELI5 先建立直觉

像把菜单放在门口：每个人拿到同一份已经印好的内容。真正的技术对应是 HTML 文件与 Web 服务器；这个类比不表示浏览器不能运行 JavaScript。

02起点 · 让网站能办事

动态网站

页面如何从“现成文件”变成“当场生成的结果”？

在请求与响应之间插入业务程序，并把需要保留的状态放入数据库。

PRESSURE 压力从哪里来

书店开始在线销售。用户甲只能看甲的订单，用户乙只能看乙的订单；价格和库存随交易变化。为每一种用户与库存组合预先制作网页不现实。

ELI5 先建立直觉

从“发菜单”变成“接单后查看账本再答复”。程序负责执行规则，数据库负责保存账本；数据库并不会替你自动写对业务规则。

STEP 01

校验身份与输入

GET /orders/1042 到达程序。程序确认请求者有权读取这笔订单，而不是只信任路径里的编号。

STEP 02

处理业务与数据

读取订单记录，决定哪些字段可以返回。下单则需要写入数据，处理失败与并发。

STEP 03

生成响应

把结果填进 HTML 模板后返回。以后也可以返回 JSON，动态处理并不限定响应格式。

再下潜一层

DEEP / 机制 · 状态 · 失败边界

常驻进程为什么更省重复工作

FastCGI 的关键之一是允许工作进程在处理请求后继续存在。程序启动、加载依赖、初始化环境不必为每次访问从头再来；代价是进程要持续占用资源。[03]

数据库持久化与进程内存不同

应用重启不应让已确认订单消失。数据库事务还可以把相关修改作为一个提交单元；但事务范围、隔离级别、错误处理仍必须正确设计。[05]

最容易误解的边界

“有数据库”不等于“不会超卖”；“服务器常驻”也不等于可以把所有用户状态随意存在静态变量里。[01][02][03][05]

分层单体

代码越来越难改，为什么先分职责，而不是先拆服务器？

把代码按变化原因组织，仍然保留一个主要部署单元。

DEEP / 机制 · 状态 · 失败边界

MVC 与三层架构不是同义词

MVC 区分 Model、View、Controller；Controller—Service—DAO 常用于描述应用分层。二者可以组合。Service 不等于 View，Model 也不是“数据库表”的机械别名。[04]

一次下单的真正不变量

本例要求库存不能小于 0，且成功创建订单时必须对应扣减库存。在同一本地事务中执行条件更新，并检查受影响行数，可以把检查与修改结合；还需处理事务冲突、重复下单和其他失败。[05][34]

单体不等于单机

单体是主要业务代码的部署边界；同一个 shop.jar 可以运行多个实例，也可以连接远程数据库。分层是逻辑结构，部署是物理结构。[15][16]

最容易误解的边界

事务解决一组操作的提交边界，不会自动修复错误的并发逻辑。过多没有实际职责的层，也可能降低可维护性。[04][05][34][15]

集群与共享状态

多加一台应用，为什么用户反而掉登录？

复制执行能力之前，要处理原来藏在单个实例里的私人状态。

PRESSURE 压力从哪里来

先把应用和数据库放在合适的独立资源上，减少争抢；应用仍吃紧时，可以升级机器，也可以运行多个应用副本。问题是：原来只有 A 认识这个已登录用户。

ELI5 先建立直觉

开两个服务窗口能分担人流，但如果顾客档案只放在窗口 A 的抽屉里，窗口 B 就无法接着服务。共享档案不等于没有档案。

01 / FLOW 一次请求 / 事件怎样走

STEP 01

第一次到 A

用户登录，A 生成会话。浏览器后续携带会话标识，例如 Cookie 中的 sid。

STEP 02

第二次到 B

负载均衡把请求交给 B。若会话只在 A 内存中，B 找不到对应记录。

STEP 03

共享状态

A 与 B 都从共享会话存储读取 sid 对应的数据；关键文件也不只存某个实例的本地目录。

DEEP / 机制 · 状态 · 失败边界

无状态不是没有状态

所谓无状态应用，通常指关键会话和持久业务状态不依赖某个应用副本的私人内存。数据被放到合适的外部存储，或在协议中显式携带。[06][07]

共享状态的代价没有消失

共享会话让应用实例不必各自保存完整会话，但共享存储的容量、过期管理和可用性成为共同依赖。应用副本扩容，不能替代共享存储自身的故障设计。[06][07]

副本与高可用要分开判断

两个应用能减少对一个应用进程的依赖，但若入口、数据库或共享会话仍有不可接受的单点，整体高可用并未自动完成。[06][07]

最容易误解的边界

扩容应用时也要控制总数据库连接数。多个应用实例可能一起把更大的压力传给同一个数据库。[06][07]

缓存与 CDN

同一个答案，为什么要每次重新查询？

复制可以复用的结果来减少工作，同时明确允许它旧多久。

命中率怎样改变数据库压力

教学简化：每次未命中只触发一次数据库读，没有其他流量，则数据库读请求约为 Q × (1 − H)。H 是命中率。这个算式解释减少的工作量，不代表端到端性能提升同比例。[08]

删缓存也不是强一致性证明

先改数据库再使缓存失效，是常见旁路缓存流程，但两步之间可能失败；并发读还可能把旧值重新填回。对强一致性敏感的决定，不应只依赖普通缓存副本。[08]

不能把所有人的页面混在一起缓存

HTTP 私有缓存与共享缓存不同；个性化内容的缓存控制和缓存键必须体现隔离边界。缓存命中率再高，也不能以串用户数据为代价。[09]

何时值得把本地方法调用变成一次网络调用？

服务大小不是核心判据

微服务的价值更接近围绕业务能力、独立部署、明确责任；不是“每张表一个服务”。如果一次小改动仍需所有服务同步发布，就没有得到预期独立性。[15]

共享物理数据库不等于共享所有权

不同服务可以在过渡阶段共享基础设施，但直接跨服务修改彼此的表会形成隐式耦合。独立演进需要管理数据访问契约，而不是只创建不同进程。[15]

模块化是可验证的工程工作

最容易误解的边界

微服务未必更快；很多本地调用变成网络调用后，单次请求反而可能更慢。独立性是收益，分布式协调是成本。[14][15][16]

LAB 05

“只多试两次”，为什么最后变成 27 次？

调整层数与总尝试次数，观察多层重试的乘法效应。

这是错误持续、预算足够且错误逐层返回时的最坏情形上界。实际熔断、截止时间与非重试错误会截断尝试；不是故障概率或性能测试。

再下潜一层

DEEP / 机制 · 状态 · 失败边界

超时表达的是“我没等到”，不是“对方没做”

下游可能已经提交操作，只是响应丢了。再次执行可能重复扣减或重复创建。要用业务请求标识与状态查询等机制处理未知结果。[20]

熔断与隔离解决不同问题

熔断器达到失败条件后快速拒绝正常调用，并在合适时机试探恢复；隔离则限制某个依赖能够占用的并发、线程或连接。它们不会修复下游错误，只帮助控制影响。[21][36]

重试的乘法效应

教学最坏情形：L 层串行依赖，每层对下一层最多尝试 A 次，且错误一路向上传播，最深层最多承受 A^L 次尝试。3 层各 3 次就是 27 次；这里“3 次”包含首次。[20]

三种证据要串起来

指标回答“整体发生了什么”；链路追踪回答“一次请求经过哪里、花多久”；日志记录具体事件。需要传播关联上下文，异步任务也应尽量保留关联。[22]

最容易误解的边界

降级必须真实表达能力下降，不能把“尚未确认支付”显示为“支付成功”。监控采样与敏感字段脱敏也应纳入运行设计。[20][21][22][36]

Outbox 的真正保证范围

订单与事件意图在同一本地事务内一起提交。它不保证消息只发一次、不保证消费者成功、不保证跨服务整体立即一致。发布器还要处理领取、重试、交接状态及所需的顺序。[23]

幂等不是“先查一下有没有”

如果两个并发消费者都先查到没有，再各自加积分，就仍会重复。常见方案是业务键唯一约束，并让去重记录与业务修改处于同一本地事务；外部副作用需要对应系统的幂等或确认协议。[13][23][34]

Saga 不是把时间倒回去

已发送邮件不能“没被看过”；支付后的退款也是新的业务动作。补偿可能失败，不能简单覆盖其他并发修改。需要可持久恢复的状态、有限重试、告警和必要的人工处理。[24][35]

常见本地事务管理器约束的是其管理的资源与执行上下文。外层方法写了 @Transactional，不会自动把一个普通 HTTP 调用纳入同一个跨系统原子事务。[37][38]

DEEP / 机制 · 状态 · 失败边界

镜像、容器、虚拟机分别是什么

镜像是运行所需文件与配置等的打包；容器是按相应隔离机制运行的进程。典型容器共享宿主侧内核，虚拟机则提供另一层系统环境。因此镜像并非无条件跨所有操作系统与 CPU 架构运行。[30]

声明期望状态，不等于业务自动正确

你可以要求 3 个副本，平台努力让实际状态符合目标。但进程活着不代表已经能服务；重启也无法修复错误 SQL、数据损坏或幂等漏洞。[31]

发布也是兼容性问题

新旧实例可能短暂共存，接口与数据库变更要容忍这个窗口。回滚应用镜像不代表数据库迁移或外部副作用会一起回滚；本例把兼容、观测和回退作为发布设计条件。[31]

最容易误解的边界

容器化不是微服务的同义词，单体也能容器化；Kubernetes 不是可靠性的免检证。备份、恢复、权限与容量仍要验证。[30][31]
