01 /先弄明白：为什么需要 MQ？

一个支付服务 · 两种独立的后续工作

支付服务Producer
支付成功 M101
→
Broker / PAYMENT_EVENT保存一份事件，按订阅规则分发
→
G_POINT积分消费组：增加积分
G_NOTICE通知消费组：发送短信

不是把原始消息复制成两份独立的 Topic 队列；而是不同消费组维护各自订阅和消费进度。发送成功也不等于每个业务端都已处理成功。

①

消费组 Consumer Group

同一业务任务的消费者组成团队。组间可以独立订阅同一消息；组内实例共同分担工作。

关键：分组独立进度 / 订阅一致性
②

重试 Retry

消费者失败或超时，Broker 按策略再次投递。成功确认后，当前消息的重试生命周期结束。

关键：重试上限 / 间隔 / 幂等
③

堆积 Lag

组内消费赶不上生产，待处理量和等待时间逐渐增大；与单条消息失败不是一回事。

关键：Topic + Group 视角
④

死信 DLQ

反复处理仍失败的异常消息进入死信处理流程，等待排查、修复和受控重新投递。

关键：死信不等于业务成功
⑤

Tag 标签

同一 Topic 可用 Tag 筛选不同消息子集，不同组可以分别订阅不同 Tag。

关键：同组所有实例过滤规则一致
⑥

幂等 Idempotency

网络故障会导致重复投递。业务应允许“同一事件被重复执行请求”，但副作用只生效一次。

关键：数据库唯一约束 + 本地事务

03 /Deep：还原真实机制
进度、重试和积压彼此相关但不相同

 
组间独立，组内分摊
G_POINT 订阅支付成功，G_NOTICE 可以同时订阅。两个组拥有各自消费进度。同组启动多个实例，提高吞吐并容灾，但不是每个实例都收到每一条。5.x gRPC PushConsumer 默认按消息粒度分配；传统 4.x Remoting 客户端一般按队列粒度分配。
重试到底何时发生？
PushConsumer 监听器返回 ConsumeResult.FAILURE 或处理超时，Broker 依重试策略重新投递。若最大重试次数设为 2，代表首次 + 2 次重试，共 3 次机会。普通消息通常按递增间隔；顺序消息的策略不同。
堆积到底在哪里？
消息实际保存在 Broker 的 Topic 队列里；不同 Group 维护自己的消费位置。堆积是 某 Topic 下某消费组的未完成工作量，不是生产者线上单独的一条“未发出队列”。PushConsumer 本地缓冲也可能排队。
DLQ 会自动恢复吗？
不会。重试耗尽进入死信后，原消费流程停止。需要查询失败原因、核验业务状态、修复、幂等校验并在授权下重新投递。不能把“转入死信”误当成业务成功。

 
用 offset 理解“堆积”：简化数量模型
1,000Broker 队列最大位点
650消费组已提交位置
350近似未完成条数
单队列简化：MaxOffset − ConsumerOffset = 350。生产监控应使用 Topic + Group + 队列范围，并区分 Ready、Inflight、重试等待与消费延迟；5.x 中只看这一个差值不等于所有状态的真实库存。对有过滤条件的订阅尤其不要直接把原始 Topic 位点差当作“可消费匹配消息数”。
消费重试解决偶发处理失败；消息堆积需要通过容量、下游限流、扩容或隔离处理。不要用无限失败重试来代替流量控制。

 
同一 Topic、不同 Tag，三个常见布局
布局实际效果是否推荐
G_A 订阅 POINT，G_B 订阅 NOTICE各自获取匹配子集、独立失败和进度适合独立业务流程
G_A 的 C1 订阅 POINT，C2 订阅 NOTICE同组实例订阅关系不一致，可能漏消费或混乱不推荐
G_A 两实例都订阅 POINT||NOTICE组内共同消费两类消息，不能保证同实例各拿一份仅在确属同一业务职责时可用

 
生产故障观察指标
症状优先观察常见处理
消费一直慢rocketmq_consumer_ready_messages、rocketmq_consumer_lag_latency、消费耗时确认生产/消费速率，查数据库、线程池瓶颈，合理扩容
消费者长时间卡顿rocketmq_consumer_inflight_messages、本地缓存、请求超时排查慢业务、锁等待、线程饥饿和网络连接
大量消息进入死信rocketmq_send_to_dlq_messages_total、异常类型、业务事件 Key先修复根因，受控回放与幂等核验
这些官方观测指标从 RocketMQ 5.1.0 开始引入；具体可用性随版本、部署组件及导出配置变化。




04 /Java：把演示变成业务代码
官方 5.x gRPC Java SDK API 风格

 
示例约定：PAYMENT_EVENT 主题、PAID 标签、G_POINT 消费组。集群需 RocketMQ 5.x、启用 gRPC Proxy。将端点改为你的环境，预先创建 Topic / Group。片段为教学模板，省略工程依赖管理、完整 Spring 启动配置和生产化监控。
Producer：事件写入 Broker，仅代表消息发送成功，不代表所有消费业务完成。


ClientServiceProvider provider = ClientServiceProvider.loadService();
String topic = "PAYMENT_EVENT";
ClientConfiguration cfg = ClientConfiguration.newBuilder()
    .setEndpoints("127.0.0.1:8081") // 5.x gRPC Proxy
    .build();
Producer producer = provider.newProducerBuilder()
    .setClientConfiguration(cfg)
    .setTopics(topic)
    .build();

String eventId = "evt-20261010-001";
String json = "{\"eventId\":\"" + eventId
    + "\",\"orderId\":\"O1001\",\"amountFen\":10000}";
Message message = provider.newMessageBuilder()
    .setTopic(topic)
    .setTag("PAID")
    .setKeys(eventId)
    .setBody(json.getBytes(StandardCharsets.UTF_8))
    .build();
try {
    SendReceipt receipt = producer.send(message);
    System.out.println(receipt.getMessageId());
} finally {
    producer.close();
}
// 真正业务中建议事务性 Outbox，避免数据库提交与发 MQ 双写不一致。


ClientServiceProvider provider = ClientServiceProvider.loadService();
ClientConfiguration cfg = ClientConfiguration.newBuilder()
    .setEndpoints("127.0.0.1:8081").build();
FilterExpression filter =
    new FilterExpression("PAID", FilterExpressionType.TAG);
ObjectMapper mapper = new ObjectMapper();

PushConsumer consumer = provider.newPushConsumerBuilder()
    .setClientConfiguration(cfg)
    .setConsumerGroup("G_POINT")
    .setSubscriptionExpressions(
        Map.of("PAYMENT_EVENT", filter))
    .setMessageListener(view -> {
        try {
            ByteBuffer buf = view.getBody();
            byte[] bytes = new byte[buf.remaining()];
            buf.get(bytes);
            PaidEvent event = mapper.readValue(bytes, PaidEvent.class);
            pointService.addPointsOnce(event); // 本地数据库事务
            return ConsumeResult.SUCCESS;
        } catch (Exception ex) {
            log.error("消费失败，等待重试，messageId={}",
                view.getMessageId(), ex);
            return ConsumeResult.FAILURE;
        }
    }).build();

// 维护 consumer 单例，应用关闭时调用 consumer.close()。
record PaidEvent(String eventId, String orderId, long amountFen) {}
// 同组所有实例必须使用相同的 Topic/Tag 订阅规则。


-- PostgreSQL 示例：组 + 事件唯一约束
CREATE TABLE consumed_event (
  consumer_group varchar(80) NOT NULL,
  event_id varchar(100) NOT NULL,
  PRIMARY KEY (consumer_group, event_id)

-- 在同一个数据库事务中：
BEGIN;
INSERT INTO consumed_event (consumer_group,event_id)
VALUES ('G_POINT','evt-20261010-001')
ON CONFLICT DO NOTHING;

-- 仅插入 1 行时才执行业务副作用：
UPDATE customer_points
SET balance = balance + 100
WHERE customer_id = 'U1001';
COMMIT;

-- Spring Java 服务中的关键结构：
@Transactional
public void addPointsOnce(PaidEvent e) {
    int n = jdbc.update(
      "INSERT INTO consumed_event(consumer_group,event_id) " +
      "VALUES (?,?) ON CONFLICT DO NOTHING",
      "G_POINT", e.eventId());
    if (n == 0) return; // 重复事件，已处理
    jdbc.update(
      "UPDATE customer_points SET balance=balance+? " +
      "WHERE customer_id=?",
      calculatePoints(e), resolveCustomerId(e.orderId()));
}
// 事务回滚后，去重记录和加积分都不会被提交。
// 用户与积分规则须来自可信业务数据源并校验。


// PushConsumer：listener 返回 SUCCESS / FAILURE。
// SimpleConsumer：应用显式 receive 并在处理成功后 ack。
// 以下为核心调用示意，省略初始化参数与循环生命周期。
List<MessageView> views =
    simpleConsumer.receive(10, Duration.ofSeconds(30));
for (MessageView view : views) {
    try {
        businessService.process(view);
        simpleConsumer.ack(view); // 确认成功
    } catch (Exception ex) {
        // 不 ack。InvisibleDuration 过后可再次被投递。
        log.error("等待可见性超时后重试", ex);
    }
}
// SimpleConsumer 的 InvisibleDuration 要覆盖业务处理时间，
// 否则未处理完就可能重新变为可见，形成重复投递。
// 重试上限由消费组策略管理。

06 /实践任务：亲手制造一次积压与死信
循序完成，适合本地 Docker + Spring Boot
  1. 建立 PAYMENT_EVENT 主题，以及 G_POINT 和 G_NOTICE 两个组，发送 10 条 PAID 消息。
  2. 让积分消费组返回 SUCCESS，通知消费组前两次失败、第三次成功，观察重投日志。明确重试次数与总投递次数的区别。
  3. 让通知组持续返回 FAILURE，设置有限重试，观察死信出现；积分组仍应保持正常。
  4. 限制通知组每秒只能处理 4 条，同时发送 10 条/秒，观测 lag 随时间增长，并排查吞吐瓶颈。
  5. 引入数据库唯一约束（消费组 ID + 事件 ID），故意在业务提交后、ACK 前模拟宕机，验证重新投递不会重复增加积分。
  6. 设计死信处置 SOP：记录原事件、异常原因、业务状态校验、审批回放、回放后校验与审计。
任务需自备实际环境才能执行。此 HTML 仅是可离线交互的教学模拟，不会连接 RocketMQ、不读取本地数据，也不会发送消息。
