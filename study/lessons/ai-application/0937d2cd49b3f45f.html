这次的学习目标

分清：模型能回答什么，应用还要补什么

这里先聚焦使用现成大语言模型开发应用：例如文档问答、内容整理、业务助手和 Agent。大语言模型（LLM）是能理解和生成语言的模型；应用是围绕用户任务组织输入、模型、数据、操作和结果的程序。

AI 应用的范围还包括传统图像识别、推荐、预测等，那些方向会增加各自的数据与建模知识。本页先把大模型应用的共通知识讲清。

同一个助手 · 问题一

“普通商品一般多久发货？”

给出发货规则，模型可以根据材料整理回答。材料很少时，直接把这几行放进输入就够用。

同一个助手 · 问题二

“订单 A102 已经发货了吗？”

规则不能证明某个订单的状态。应用要取得经过授权的订单数据，再把结果交给模型解释。

本单元验收：遇到一个新需求，能说明缺的是任务定义、材料、真实数据、执行能力，还是结果检查。现在先建立地图；地图里的全部知识不用今天学完。

本页订单、规则和工具返回值均为虚构教学材料；交互使用预设推演，没有连接模型或真实业务系统。

一个核心关系

应用负责连接，模型负责产生候选结果

点击四个节点，查看各自职责。双向箭头表示请求与返回。

应用程序

它安排数据怎么流动：接收问题、选择资料、调用模型、核对工具权限、处理失败、展示结果。即使界面看起来只是一段聊天，这些工作仍然要有人实现。

上下文（Context）是模型本次实际收到的信息，例如任务要求、用户问题、选出的文档、历史消息和工具返回值。

把数据存进数据库，不代表模型就能使用；应用要把需要的信息取出，再放入这次调用中。模型写出“已查询”也不代表查询真的发生。

本图画的是职责边界，不限定代码必须运行在同一台机器；某些平台会代管工具执行，执行结果仍须核验。[3][4]

需要掌握哪些知识

“先学”是建立最小能力；“按需加入”由任务决定；“从头贯穿”在第一版就保留最小检查，再随着使用范围扩大而完善。点击卡片查看是什么、为什么、学到什么程度。

三个常见误区：有正确格式，不代表内容正确；给了资料，不代表答案一定有依据；工具调用请求生成成功，不代表业务操作执行成功。

第一课 · 一个完整的小示范

把材料变成可检查的回答

目标：输入几条商品规则和一个问题，得到答案、来源编号、缺少的信息。这里先手工把材料放进输入，不需要建数据库或使用框架。

JSON 是一种机器容易读取的数据写法。例如 {"answer":"48 小时内"} 中，answer 是字段名，后面是它的值；[] 表示一个列表，空列表表示没有条目。

准备材料

D1

普通商品在支付后 48 小时内发货。

D2

预售商品按商品页标注的日期发货。

D3

发货后可在订单详情查看物流单号。

操作顺序与原因

  1. 复制下面的提示词，在你已有的对话工具中新建会话并粘贴。这里只用虚构材料。
  2. 检查输出是否有三个字段；固定字段便于程序接着处理。
  3. 检查答案是否由 D1 支持；有来源编号还不够，来源内容必须真的支持结论。
  4. 把问题替换成具体订单状态，再看模型是否指出信息缺失。保持其余内容不变，便于比较差别。
任务：只根据下列资料回答用户问题。
规则：
1. 不补造资料中没有的信息，不声称已查询任何系统。
2. 引用真正支持答案的资料编号。
3. 如果信息不足，说明无法确定，并列出缺少的信息。
4. 只输出 JSON，包含 answer、source_ids、missing_data 三个字段。
   answer 是文字；source_ids 和 missing_data 是文字列表。

资料：
[D1] 普通商品在支付后 48 小时内发货。
[D2] 预售商品按商品页标注的日期发货。
[D3] 发货后可在订单详情查看物流单号。

问题：普通商品一般多久发货？

参考输出

{
  "answer": "普通商品在支付后 48 小时内发货。",
  "source_ids": ["D1"],
  "missing_data": []
}

执行说明：这是根据材料手工编写的参考结果，没有调用模型 API。页面交互只演示机制。实际模型的措辞可能不同；关键是内容有依据、字段可读取、缺失信息不编造。

验收怎么做

① 三个字段完整且类型合适；② 答案保持“支付后”与“48 小时内”的含义；③ D1 确实支持答案；④ 没有把“发货”改成“送达”。

最可能卡在哪里

如果返回一段普通文字，先核对格式要求。接入程序时，可按供应商文档使用结构化输出，再由程序检查字段和值。结构化输出主要约束形式，仍然可能出现事实错误。[5]

从第一版起留几条检查样例

输入变化预期行为检查什么
普通商品多久发货？引用 D1，回答支付后 48 小时内。正常情况
预售商品也保证 48 小时内发货吗？引用 D2，按商品页日期；不能套用 D1。适用范围
这段资料没有写到的问题指出缺少信息，不补造答案。资料不足
普通商品多久送达？资料只有发货期限，无法确定送达时间。相近词的区别

这四条是起点，不是完整质量保证。后续加入订单工具时，再检查“查不到订单”“无权访问”“超时”等情况。改变模型或提示词后重跑相同样例，才知道改动是改进还是退步。[6]

从做出功能，到独立处理变化

建议按这个顺序学

以下是学习安排建议，不是行业统一标准，也不承诺在固定周数内掌握。每阶段先取得右述证据，再决定是否增加能力。

定义一个小任务，先做手工样例

例如本页的“根据材料答问题”。写出输入、输出、未知时的行为，再准备正常和失败样例。

完成证据：能判断一个答案为何合格，而不只是觉得它很流畅。

在程序里完成一次模型调用

把材料和问题发送给模型服务，接收结果，处理失败。API 是程序请求另一项服务的接口；HTTP 是常见的网络请求规则。先理解一次请求如何往返。

完成证据：能独立换一个问题，并处理没有返回结果的情况。

让返回结果能被检查和使用

学习 JSON、字段约束和程序校验；把缺失值单独表示。保留输入、模型版本、提示词版本和失败信息，方便定位问题。

完成证据：能发现“格式正确但来源不支持”的错误。

遇到信息缺口，加入一种需要的能力

材料太多时学习检索；需要实时状态时接入一个只读工具。两者解决不同问题，可以只需要其中一种。

完成证据：能分别定位“没找到资料”“查错对象”“模型误读结果”。

任务确实需要动态决策时，再学习 Agent

固定步骤先写成工作流。若下一步取决于工具返回结果，再允许模型在明确范围内选择动作；加入步数、时间、费用上限和失败出口。

完成证据：能解释为何继续、为何停止，并验证实际执行结果。

让目标用户试用，检查运行与价值

提供界面或接口，配置访问权限、密钥、日志和成本统计，观察失败与反馈。上线前的基本保护不能留到出事后再做。

完成证据：别人在你的帮助之外也能完成任务；你能从记录定位一个失败。

编程语言如何选

优先使用你已经能写、能调试的语言。你之前提过 Java 开发；如果 Java 对你更顺手，可以从 Java 接口调用开始。若当前编程也需补基础，就围绕读写数据、调用接口和处理错误补，不同时学多门语言。

已有职业经历不等于已掌握这里的每个知识点，是否跳过基础以实际操作为准。

第一轮可以暂缓什么

从零预训练模型、系统学习全部高等数学、复杂 GPU 集群、多 Agent 协作、同时研究多个框架。需要深入模型行为、微调或本地部署时，再补相应理论与运行知识。

暂缓不代表永远无用，而是先保证当前小任务能够完成并被检验。

如继续采用每周约 9 小时的投入偏好，可试分为：3 小时学当前卡点、4 小时做和改一个功能、2 小时整理失败样例与复盘。可按实际情况调整；本页没有创建任何定时安排。

避免被名词淹没

把常见术语放回它解决的问题

术语通俗含义与作用什么时候学
RAG
检索增强生成		先找到相关资料，再把资料提供给模型生成回答。可以用关键词、向量或混合检索，不等于一定要上向量数据库。材料多、会更新，或需要引用出处时。[2]
Embedding
向量表示		把文本等内容映射为一组数字，用来比较某种相似性；相似不代表事实正确，也不代表有权访问。需要语义检索等相似性任务时。
Tool Calling
工具调用		模型产生工具名和参数，由应用或运行环境检查并执行，执行结果返回后再继续处理。需要查真实数据、计算或执行动作时。[3]
Workflow / Agent
工作流 / 智能体		本课约定：工作流的主要路径由程序预先确定；Agent 可根据目标与反馈动态选下一步行动。两者可组合。单次调用不足以完成任务时。[1]
Agent Harness
智能体运行支撑		不同产品范围不完全相同，通常指管理状态、工具执行、权限、重试、停止和记录等的外层运行系统。需要控制多步任务的执行过程时。
MCP
模型上下文协议		让应用以共同协议发现并使用工具、资源等能力。连接方式统一，仍须处理授权、数据和业务规则。多个工具或客户端需要复用连接时。[7]
Skills
技能包		把任务方法、说明以及可选的脚本和材料打包，按需要载入。它不会自动改变模型的训练参数。同类任务的方法需要重复使用时。[8]
Hooks / Plugins
事件钩子 / 插件		以 Claude Code 为例：Hooks 在特定事件发生时触发处理；插件把技能、钩子、工具连接等组合成一个扩展包。其他产品须查各自定义。扩展开发工具或复用工程流程时。[9][10]
Fine-tuning
微调		用训练数据进一步调整已有模型参数。适合某些稳定行为或格式任务；持续变化的业务事实仍需要数据更新与访问机制。先有评估证据表明提示、资料或流程改进仍不足，再研究。

AI 编程助手可以辅助写代码、解释错误和改测试。学习时仍要能说清输入输出、检查改动和解释失败。会安装工具、跑通别人的示例，只能证明完成了这些操作。

如果以后做语音、图片或视频应用，还加什么？

根据目标加入对应的输入输出处理：语音识别把声音转成文字，语音合成把文字变成声音；图片可能需要文字提取或视觉理解；视频还要处理时间轴、镜头与音画同步。也要检查数据授权、生成质量、处理时延和费用。这些是方向分支，不是所有文本应用的先修课。

一个主要动作 · 检查理解

把“规则问题”换成“事实问题”

只给 D1–D3 三条规则，没有订单数据库或工具返回值。现在用户问：“订单 A102 已经发货了吗？”你会怎样回答？还缺少什么信息，应由哪个环节取得？请说明为什么。

需要一点提示

“通常在 48 小时内发货”和“A102 已经发货”是同一类事实吗？检查 D1–D3 是否包含 A102 的任何状态记录。

完成后，再查看参考依据

可答：“现有资料仅说明发货规则，无法确定 A102 是否已经发货；需要查询该订单的当前状态。”三条规则没有提供这个具体订单的状态。

若应用已有订单查询能力，应先核对用户是否有权查看该订单，再由应用或可信运行环境执行查询，取得结果后让模型解释。没有查询能力时，应明确说明限制，而不是声称已经查询。即使系统支持工具调用，也要以真实执行结果为依据。

这说明：规则资料解决“通常如何”，订单数据解决“这一次实际如何”；换一个更强模型不能补出未提供、也未通过工具取得的私人业务事实。

经对话验证的能力：待验证。本页不会因点击、阅读或自评自动标记“已掌握”。把答案带回对话后，才能根据理由给出反馈。

回答与自评可保存在当前浏览器；是否保留取决于打开方式与浏览器设置，不保证跨设备同步。
