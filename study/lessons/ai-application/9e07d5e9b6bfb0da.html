01 · FIRST PRINCIPLES

先理解：AI 应用究竟是如何工作的？

一个最贴近业务的例子

用户问：“我的订单什么时候发货？公司退款规则是什么？”

模型可以理解问题，但不能凭空知道实时订单状态或企业最新政策。

应用程序必须查询订单接口、检索授权政策，再让模型组织成可核对的回答。

① 用户提出任务订单状态 + 退款规则
↓
② 应用程序负责组织与控制认证 · 任务编排 · 参数校验 · 错误处理
↓
大模型理解/生成
知识检索政策依据
业务工具订单状态
↓
③ 校验并返回结果答案 + 来源 + 错误/未知说明
注意：这是关系图，不是真实 API 调用记录。模型可能先请求工具、再使用结果生成答案；工具的实际执行由应用程序掌控。

03 · PROJECT-FIRST ROADMAP

按项目学习，而不是先把所有理论学完

下列时间仅供安排练习，不承诺固定周数学会；按实际掌握情况推进。

阶段 A · 起步（约第 1–2 周）

模型调用与结构化输出

任务输入、Prompt、API 调用、JSON、失败处理。

交付物：会议纪要 → 可校验的待办清单。
阶段 B · 数据（约第 3–4 周）

让回答有可靠依据

文档解析、检索、引用、拒答与数据权限。

交付物：带来源的文档问答助手。
阶段 C · 行动（约第 5–6 周）

连接一个真实只读工具

Tool Calling、参数校验、工具结果、失败分支。

交付物：能查订单但不能越权的助手。
阶段 D · 编排（约第 7–8 周）

必要时升级 Workflow / Agent

条件路由、循环、停止条件；需要标准化工具集成时再学 MCP。

交付物：可追踪的两步业务工作流。
阶段 E · 可靠（约第 9–10 周）

评估、安全与工程化

测试集、提示词注入、权限、成本、超时、监控。

交付物：通过基础测试并能展示失败原因。
阶段 F · 产品（约第 11–12 周）

部署一版真正有人使用的 MVP

界面、鉴权、部署、反馈、迭代；根据用户需求优化。

交付物：一个可演示、可复盘的最小产品。
技术选型不要反过来支配学习：可以用 Java + Spring Boot + Spring AI 构建；也可以用 Python 或 TypeScript。第一目标是跑通“模型 + 数据/工具 + 业务规则 + 验收”。LangChain、LangGraph、多 Agent 和向量数据库等都不是每个小应用必须先学的。
04 · A FIRST MINI LESSON

第一个 30 分钟练习：把自然语言变成可靠数据

只做一个可手工验证的例子；本页不调用模型，也不会消耗 API 额度。

输入：会议记录

“周一产品会上决定：小李负责整理 FAQ，周五前完成。小王负责梳理客户反馈，时间还没定。”

目标：把待办转换成程序可处理的字段；不得补造未出现的日期。

向模型提出的要求
从以下会议记录提取待办。 只输出结构化数据。 字段：task、owner、deadline。 原文没有的信息填“未提供”。 不要推测具体日期。
手工推演的期望输出
[ { "task": "整理 FAQ", "owner": "小李", "deadline": "周五前" }, { "task": "梳理客户反馈", "owner": "小王", "deadline": "未提供" } ]

为什么需要结构化输出？页面、数据库和其他系统可以按固定字段读取结果；但字段格式正确并不代表内容事实正确，仍需对照原始记录。

下一轮升级：改成真正的模型 API 调用；通过 JSON Schema 限制输出形状，再处理“模型输出字段正确但提取事实不对”的情况。
