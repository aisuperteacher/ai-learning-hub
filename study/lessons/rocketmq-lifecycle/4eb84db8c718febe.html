角色卡：先知道“谁负责什么”

先有位置，再记术语。

Producer
发消息的人
构造 Message、查路由、选 Queue、发给 Broker
NameServer
导航 / 通讯录
维护 Topic ↔ Broker/Queue 路由；不承载业务消息正文
Broker
真正的仓库
接收、持久化、查询、向消费者提供消息
Topic
业务大类
如 ORDER_EVENT；一个 Topic 通常由多个 Queue 组成
MessageQueue
Topic 内的车道
水平分片与有序存储单元；Offset 在 Queue 内递增
Consumer Group
同一职责的处理团队

Consumer Offset
这个团队读到哪儿了
可把核心标识理解为 Group + Topic + Queue → progress
DLQ
最终失败隔离区

Broker 为什么同时有 CommitLog 和 ConsumeQueue？

一句话：正文只顺序写一份，逻辑 Queue 用轻量索引去定位正文。

CommitLog · 物理消息文件
来自不同 Topic / Queue 的消息按物理写入位置排列（示意）
1000ORDER_EVENT / Q1 / order=10080
1260USER_EVENT / Q0 / user=9527
1450ORDER_EVENT / Q1 / order=10086
1730PAY_EVENT / Q2 / pay=P9001
←
ConsumeQueue · 逻辑队列索引
ORDER_EVENT / Q1
QOffset 100→ CommitLog 1000
QOffset 101→ CommitLog 1450
QOffset 102→ CommitLog 2100
为什么这样设计？
CommitLog 追求高吞吐的顺序写；ConsumeQueue 让“按 Topic + Queue + Offset 找消息”不需要扫描整份物理日志。
消费成功 ≠ 物理删除。
RocketMQ 的消息保留按存储策略管理，与“某个 Group 是否已经消费”是两回事。

动手理解 Offset 和消息堆积（Lag）

拖动两个滑块，看“Broker 已经写到哪里”和“某 Group 已经追到哪里”的距离。

已追上
待消费
MaxOffset1000Broker 队列最新进度
ConsumerOffset800该 Group 的消费进度
Lag200还没追上的距离
Lag ≈ MaxOffset − ConsumerOffset = 200
更精确地看：通常要按 Consumer Group + Topic + Queue 观察，再把多个 Queue 的 Lag 汇总。过滤、重试、版本实现与监控口径会影响业务上对“待处理量”的解释。

为什么一定要做幂等？

MQ 的“至少一次”语义意味着：重复投递并不是异常设计之外的事情。

典型重复场景
① DB 扣库存成功业务已经生效
→
② Consumer 宕机成功结果还没可靠提交
→
③ 再投递同一业务消息再次出现
业务防线
messageKey = "ORDER_CREATED:10086" if (consume_log.exists(messageKey)) { return SUCCESS; // 已处理，直接幂等成功 } doBusiness(); consume_log.insert(messageKey, "SUCCESS");
真实项目要让“业务状态变更 + 幂等记录”满足你需要的一致性边界，例如通过唯一约束、本地事务、状态机或专门的幂等表。

4.x 和 5.x：哪些地方最容易混？

学习时先掌握共同主干，再记版本边界。

主题经典 4.x 心智模型5.x 需要补充的认识
负载均衡Queue-based：Group 内 Consumer 分 Queue；Queue 少于 Consumer 时会有实例拿不到 Queue。PushConsumer / SimpleConsumer 可使用 Message-based；PullConsumer 仍可表现为 Queue-based。具体取决于 Broker、客户端与 Consumer 类型。
消费 APIDefaultMQPushConsumer / PullConsumer 等经典客户端模型。PushConsumer、SimpleConsumer 等模型更明确区分拉取与可见性/状态机语义。
Retry并发消费常见默认最大重试 16；集群模式有自动 Retry；广播模式不要套用此机制。最大重试次数由 Consumer Group 元数据等配置；PushConsumer 有 Ready → Inflight → WaitingRetry → ... → DLQ 状态。
DLQ常见名称 %DLQ%ConsumerGroupName。仍是消费失败最终兜底，但以当前版本官方消费重试与 Group 配置为准。

开发 / 排障时，从哪里切入？

把症状映射回消息生命周期。

Producer 发不出去看路由获取、Broker 可写、网络、超时、发送重试Producer → NameServer/Broker
Broker 有消息但没人消费看订阅、Consumer Group、路由、客户端存活、负载均衡Group / Consumer
消息持续堆积看每个 Queue 的 MaxOffset 与 Group ConsumerOffset、消费 TPS、业务耗时、下游 DB/RPCLag
加机器没提速4.x 先确认 Queue 数量是否已经限制 Queue-based 并行度，再查线程池和下游瓶颈Queue / Rebalance
重复扣库存不要只怪 MQ；先检查消费业务是否幂等、事务边界是否合理Idempotency
DLQ 有消息查看原业务 Key、异常原因与重试历史；修复代码/数据后走补偿或重放流程Retry / DLQ

最后只背这 8 句话

把它们当作你以后学习 RocketMQ 的骨架。

① NameServer 只管路由，业务消息由客户端直接和 Broker 交互。
② Topic 是业务分类，Queue 是 Topic 内的水平分片/有序单元。
③ Producer 查路由、选 Queue，然后把消息发到 Queue 所在 Broker。
④ Broker 以 CommitLog 存物理消息，以 ConsumeQueue 建逻辑队列索引。
⑤ Consumer Group 表示相同消费职责；同组实例共同承担消费。
⑥ 消费进度要从 Group + Topic + Queue 看，Lag 就是“Group 落后 Broker 多远”。
⑦ 失败先 Retry，多次失败才 DLQ；DLQ 是 Group 视角的最终失败区。
⑧ 重试、网络超时、Rebalance 都可能带来重复，所以消费业务必须考虑 幂等。
