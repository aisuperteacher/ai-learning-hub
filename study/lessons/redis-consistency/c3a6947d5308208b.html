01先解决一个具体问题

商品 product:42 原价 100 元。运营将它改为 120 元，数据库事务已经提交，但一些用户仍从 Redis 读到 100 元。

本单元假设：商品详情读多写少，展示允许短暂延迟；数据库是权威来源，缓存可以删除后重建。为看清核心时序，先用单个 key、数据库主库的新事务读取，不加入读副本延迟与多级缓存。

验收：你能逐步追踪数据库、缓存和请求手中暂存的值；解释为什么先提交数据库再删除缓存；指出这种顺序仍留下的一个漏洞。

本次重点是“允许短暂旧数据时如何设计”。最终结算价、扣库存、权限校验是否允许旧数据，需要单独定义要求。

02先看熟悉的办法

每次直接查数据库：如果索引合理、访问量不大，已经够用；可以先量出延迟和数据库负载，再决定是否加缓存。

增加 Redis：同一商品被反复读取时，缓存能减少重复查询。代价是系统出现两份状态，而两步远程操作之间可以插入别的请求，也可以只成功一步。

朴素做法看起来合理需要面对的反例
更新数据库，再更新缓存两边都写成新价格A 提交 120，B 提交 130；B 先缓存 130，A 后缓存 120，旧写覆盖新写。
先删除缓存，再提交数据库让后续读取重新查库提交前有读请求查到旧价 100，重新写回缓存。

这里的“双写”是对两个系统的协调修改，UPDATE 数据库 + DEL 缓存 也在这个问题范围内；不要求两边都执行 SET。

03选一个可解释的起点

读时按需缓存，写时先提交数据库，再使缓存失效。

这叫 Cache-Aside（旁路缓存）：应用自己负责读取、回源与缓存管理。删除缓存的好处是：写请求不用把可能已经过时的完整对象再覆盖进去；重建留给下一次读取。

选择它的前提是业务容忍短暂旧数据。代价包括缓存未命中后的数据库查询，以及失效失败、并发回填等后续处理。删除缓存减少了某些竞态，并没有消除全部竞态。

数据库权威数据；事务提交后，变更才正式成立。
缓存失效删除可重建的副本；空缓存是一种正常状态。
最终一致性在后续机制正常工作、旧读和写入等扰动结束后收敛；不是“放着必然会好”。

04先看写路径，再看读路径

点击“应用”“数据库”或“Redis”查看它的职责。图只表示应用的写顺序，不表示数据库会自动通知 Redis。

准确概括：数据库提交使业务变更成立；删除缓存让后续未命中的读取有机会从数据库取得新值。

读取时的三个动作

  1. GET product:42：命中就返回缓存。
  2. 未命中：查询数据库，拿到一个结果。
  3. 把这个结果用带过期时间的 SET 写回缓存，再返回。

“拿到结果”与“写回缓存”之间也可能暂停。暂停期间，别的请求可能已改完数据库并删完缓存；这就是后面要复现的关键。

两个容易混淆的判断

数据库缓存怎样判断
120空正常未命中；下一次读取应回源。
120100缓存过时；后续命中可能返回旧价。

“一致”不要求两边时时都有相同内容；需要定义读请求在什么时间、什么条件下可以得到哪些值。本单元先观察：已提交改价之后才发起的新读，是否仍命中旧价。

    先执行时序，再对照结论。

    一个完整示范：先删缓存为什么会失败？

    时刻事件数据库缓存
    t1A 先删缓存，数据库尚未提交改价100空
    t2B 未命中，查询并取得旧价格100空
    t3B 将查到的 100 回填100100
    t4A 提交价格 120，随后没有再删除120100

    结果：A 没有写错数据库，B 也没有凭空造数；操作交错后，新读仍可能命中 100。

    验收实验：场景 2 和场景 5 执行到结束后，均应出现数据库 120、缓存 100；让当前缓存过期，再发起新读，模型应变为数据库 120、缓存 120。场景 4 可通过持久化任务重试删除，再回填恢复。

    最可能的卡点：以为“数据库改完，B 手中的 100 就会变成 120”。B 持有的是先前查询的结果，不是指向数据库当前行的实时引用。切换场景会重置实验；浏览器刷新也会重置模型。

    验证范围：交付前对这 5 组预设时序及修复动作执行了模型断言。它们展示可发生的交错，不统计发生概率，也不替代真实 Redis、数据库和网络的集成测试。

    对应到服务代码：先把顺序写清楚

    // Java 风格流程伪代码：解释职责，不能直接复制编译。
Product read(id) {
  cached = cache.get(key(id));
  if (cached != null) return cached;
  product = database.readFromPrimary(id);
  cache.setWithTtl(key(id), product, ttl); // 尽力回填
  return product;
}

changePrice(id, price) {
  database.transaction(() -> {
    database.updatePrice(id, price);
    outbox.recordInvalidate(key(id)); // 与业务修改同事务持久化
  }); // 在这里已成功提交
  tryInvalidateNow(key(id)); // 加速失效；失败由持久化任务补偿
}

// 后台任务：有界退避重试；DEL 成功后才将任务标记完成。
// key 本来不存在、DEL 返回 0，也可视为失效已达成。

    这段流程让“删除意图”可恢复。Outbox（本地消息表/事务发件箱）是进阶方向；上述补偿仍不阻止场景 5 的晚回填。回填失败可记录错误并返回已查到的数据库结果；缓存读取失败后的回源要受数据库容量保护。

    06用实验结果决定改进

    本轮先记住三个边界

    1. 顺序中的“先写库”，指成功提交。在普通数据库 @Transactional 方法中写完 UPDATE 后调用 DEL，事务可能要等方法返回才提交。可以把失效绑定到 AFTER_COMMIT；但进程在提交后崩溃时，单独的内存回调不提供持久化恢复。
    2. 删除失败，需要可恢复的失效机制。先做有限重试；若要覆盖进程退出，把失效任务和业务变更放在同一数据库事务里，后台可重放。仅在失败后才往内存队列里补一条，仍有崩溃丢失窗口。任务重放 DEL 不会把旧价格写回去，但可能额外造成未命中。
    3. 删除成功，仍可能晚回填。场景 5 说明：先前已读取的旧结果可在 DEL 之后进入缓存。TTL 为当前缓存条目提供过期兜底，但不能单独承诺“提交后固定 N 秒内全局必定最新”。
    TTL 的起点：若 100 在提交后第 8 秒才回填，TTL 为 30 秒，则这个条目可留到提交后约第 38 秒。再次回填、续期、旧事务快照或落后的只读副本，还可能把窗口拉长。需要结合数据来源新鲜度与在途读取上限来推导业务界限。

    改价成功后，缓存删除偶发报错提交后失效 + 持久化补偿 + TTL提交后杀进程、让 Redis 断连；重启后任务仍能补删。增加任务处理与监控。
    DEL 成功日志存在，但旧值又出现查回填时序与读副本延迟；必要时协调读写或使用防旧回填的版本协议故意暂停旧读，再提交、删除、恢复旧读；验证旧结果被拒绝。只有 SET 时看缓存版本、缓存为空就放行，仍有缺口。
    想用“延迟双删”处理旧读提交后删除，延迟一段时间再删；保证第二次删除可恢复模拟读耗时大于延迟，旧值仍可能晚到；固定 sleep 不是严格保证，增加延迟和任务成本。
    结算不能接受缓存旧价格把关键决策放在满足一致性要求的权威读写路径，数据库事务内校验测试改价与下单并发、事务隔离和重试。读主库也要定义事务快照与业务生效规则。

    Redis 的 MULTI/EXEC 或 Lua 可以协调 Redis 内的操作；普通数据库事务协调数据库内的变更。把两者分别包起来，不会自动得到跨数据库与 Redis 的原子事务。

    稍后再研究：MQ / CDC / 锁分别补哪一块？

    MQ（消息队列）与 CDC（变更数据捕获）可驱动失效任务，仍需考虑消息可靠性、重复、积压和受影响 key；“发条消息”本身没有关上提交与发消息之间的缺口。CDC 也不会自动阻止已经在途的旧结果回填。

    仅给写请求加锁，读请求照常回填，仍可复现场景 5。需要协调所有相关的读写参与者，定义租约失效、所有权与恢复规则，才能评估保证；这些适合下一单元单独实验。

    入门可用 → 掌握 Cache-Aside 时序；正确可靠 → 提交边界、失效补偿和故障测试；特定场景优化 → 版本协议、读写协调和多级缓存。
