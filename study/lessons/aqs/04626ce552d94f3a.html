01 · 从现象理解

多个线程想同时改同一个数字，会发生什么？

线程可以理解为程序里的多个“执行者”。假设 A、B、C 三个线程都要修改同一个银行余额。若不限制并发操作，可能互相覆盖计算结果。

一个易懂的比喻只有一个办公室钥匙。A 拿走钥匙，B、C 只能登记排队。A 归还后，通知下一个人尝试领取。
真实 Java 对象钥匙资格由 state 与获取规则决定；排队者记录为队列节点；挂起/恢复由 LockSupport 协助完成。

AQS = AbstractQueuedSynchronizer，抽象队列同步器。它提供的是构建锁/同步器的底座，并不是一把直接可用的锁。具体的锁还要告诉 AQS 什么状态算成功，以及什么时候算完全释放。

比喻的边界：现实里“叫到号码”可能意味着直接领到钥匙，但在 AQS 中，唤醒只是获得再次竞争的机会，不保证已经取得锁。

03 · 理解原理

为什么只需要三个核心机制，就能管理大量线程？

01 / state

管理资格

int state 是同步状态。子类规定它代表锁的持有次数、许可证数量或剩余倒计时。compareAndSetState（CAS，比较并交换）负责安全争夺状态。

02 / Queue

管理等待者

获取失败的线程，可封装成节点进入类似 CLH 的双向同步队列；记录顺序与等待信息，处理取消、超时、中断等情况。

03 / park

管理休眠

LockSupport.park 让线程暂停继续争抢；unpark 给予恢复执行的许可。恢复后仍须重新检查能否取得资源。

核心链路：从业务代码走到 AQS

业务代码lock.lock()
申请保护共享资源
→
具体同步器tryAcquire()
规定成功条件
→
AQSacquire()
失败后组织排队
→
LockSupportpark/unpark
等待和恢复竞争

这是一张责任关系图，不代表每次加锁都会经历排队/挂起。没有竞争时，获取通常可以直接成功。

CAS 是什么，为什么不能先判断再赋值？

普通“先检查 state == 0，再写入 1”分成两步，A、B 可能同时看到 0，最终都以为自己成功。CAS 在一个原子操作里“只有当前值确实等于预期值，才完成修改”，因此两个线程争夺 0→1 时最多一个成功。

AQS 不是万能的并发安全自动机：具体子类仍要正确实现获取/释放语义、所有权及业务数据保护；AQS 本身不会自动知道“状态 1 是什么业务含义”。

04 · 容易混淆的两种模式

独占和共享，到底区别在哪？

模式直觉典型类关键判断
独占（Exclusive）同一时刻，通常只有一个线程能持有这一份独占资格ReentrantLocktryAcquire 返回布尔值，定义能否获得独占访问
共享（Shared）在资源允许时，多个线程可以同时通过Semaphore、CountDownLatchtryAcquireShared 用负数/非负数标示失败/成功，并帮助后续传播
同时支持两种读操作可共享，写操作需独占ReentrantReadWriteLock同一框架下分别处理读、写规则

例如“最多三个人同时使用会议室”可以用共享许可来想；“会议室只能有一个人使用”对应独占。共享并不是无限通行，它依然由具体状态规则限制。

05 · JDK 版本比较，基于官方源码

JDK 8、17、21 的 AQS 到底变化了什么？

三代都在 java.util.concurrent.locks.AbstractQueuedSynchronizer 中。公开的“原子同步状态 + FIFO 等待队列 + 独占/共享 + 子类实现 hook 方法”设计保持一致，显著变化发生在内部节点结构与排队算法。

版本对比最容易踩的坑：网上不少 AQS 源码教程基于 JDK 8，直接在 JDK 17/21 里搜索 Node.SIGNAL、shouldParkAfterFailedAcquire，会发现代码结构不一样。不能因为找不到旧字段，就认为 AQS 不再使用等待队列。

JDK 21 的额外背景：虚拟线程成为正式功能。AQS 相关的 LockSupport.park 与线程调度能配合虚拟线程；对可能出现长时间阻塞的代码，还要理解 JDK 21 对 synchronized 内阻塞的 pinning（载体线程固定）问题。这是 JDK 21 的线程运行时话题，不等于 AQS 整体重新发明。阅读 JDK 21 官方说明。

06 · 动手验证

只实现“什么时候能拿锁”，排队交给 AQS

下面的 MiniMutex 是为了学习设计的最小非重入、非公平互斥锁；演示了子类重写 tryAcquire / tryRelease，而 acquire / release 以及等待队列的机制由 AQS 提供。不建议当成生产级锁使用；实际业务请优先用 ReentrantLock。

AqsDemo.java · Java 8 语法兼容
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.locks.AbstractQueuedSynchronizer;

/**
 * AQS 入门教学演示：非重入、非公平的互斥锁。
 * 仅用于理解 AQS，实际业务优先使用 ReentrantLock。
 * Java 8 / 17 / 21 均可编译运行。
 */
public class AqsDemo {
    static final class MiniMutex {
        private final Sync sync = new Sync();

        private static final class Sync extends AbstractQueuedSynchronizer {
            @Override
            protected boolean tryAcquire(int ignored) {
                // CAS: 只有一个线程能把 state 从 0 改成 1。
                if (compareAndSetState(0, 1)) {
                    setExclusiveOwnerThread(Thread.currentThread());
                    return true;
                }
                return false;
            }

            @Override
            protected boolean tryRelease(int ignored) {
                if (getState() == 0 ||
                    getExclusiveOwnerThread() != Thread.currentThread()) {
                    throw new IllegalMonitorStateException();
                }
                setExclusiveOwnerThread(null);
                setState(0); // volatile 写：发布释放动作
                return true; // AQS 随后负责通知合适的等待者
            }
        }

        void lock() { sync.acquire(1); } // 抢不到时由 AQS 排队并等待
        void unlock() { sync.release(1); }
        boolean hasQueuedThreads() { return sync.hasQueuedThreads(); }
    }

    public static void main(String[] args) throws InterruptedException {
        final MiniMutex mutex = new MiniMutex();
        final CountDownLatch aboutToAcquire = new CountDownLatch(1);

        mutex.lock();
        System.out.println("主线程：已经获得锁");

        Thread worker = new Thread(() -> {
            System.out.println("工作线程：准备抢锁");
            aboutToAcquire.countDown();
            mutex.lock();
            try {
                System.out.println("工作线程：终于获得锁");
            } finally {
                mutex.unlock();
                System.out.println("工作线程：释放锁");
            }
        }, "worker");

        worker.start();
        aboutToAcquire.await();
        long deadline = System.nanoTime() + TimeUnit.SECONDS.toNanos(2);
        while (!mutex.hasQueuedThreads() && System.nanoTime() < deadline) {
            Thread.sleep(1);
        }
        System.out.println("主线程：观察到等待队列 = " + mutex.hasQueuedThreads());
        System.out.println("主线程：准备释放锁");
        mutex.unlock();
        worker.join();
    }
}

在 Windows 或其他支持 Java 的系统中运行

javac -encoding UTF-8 AqsDemo.java
java AqsDemo

如果电脑安装多个 JDK，可在分别选择 JDK 8、17、21 后运行同一个程序。它不需要任何第三方依赖。

  1. 主线程执行 mutex.lock()，state 从 0 被设置为 1。
  2. 工作线程执行 mutex.lock()；由于状态占用，tryAcquire 返回 false，AQS 负责将它加入同步队列等待。
  3. 主线程 mutex.unlock()，tryRelease 将状态改成 0；AQS 有机会通知队列中的等待线程。
  4. 工作线程被恢复并再次尝试成功，进入临界区，最后在 finally 中释放锁。
代码在 JDK 21 环境中实际编译运行过，并通过 javac --release 8 编译检查 Java 8 接口兼容性；没有在真实 JDK 8、JDK 17 运行环境中逐个执行，因此不将它们标记为已实测。

07 · 防止学偏

四个经常被错误理解的细节

① FIFO 队列，不意味着必然严格公平

AQS 使用 FIFO 形式组织等待节点，但具体获取算法可选择非公平策略。new ReentrantLock() 默认非公平；即使 B 比 D 更早排队，在特定竞态下 D 也可能先获取。是否采用公平策略需要看具体锁的实现。

② unpark 不等于“把锁交给别人”

unpark 只是给目标线程恢复执行的许可。它醒来后要重新检查获取条件；另外 park 也可能因中断或虚假唤醒返回，所以必须配合循环与状态检查。

③ AQS 同步队列 ≠ Condition 条件等待队列

condition.await()主动释放当前锁并进入条件等待队列
→
condition.signal()将一个等待者转去争夺锁的同步队列
→
重新获取锁成功后 await() 才能返回继续执行

所以 signal() 并不保证被通知的线程马上执行其后面的业务代码；它依然需要重新获得锁。

④ synchronized 不是由 AQS 实现的

synchronized 主要依赖 JVM 的监视器（monitor）机制；ReentrantLock 则是使用 AQS 的典型锁实现。它们都能实现互斥，但底层机制不同，不能混成同一个东西。

08 · 检查是否真正理解

用一个反例检验，而不是只背定义

问题 1：线程 B 已经被 unpark，是否意味着它一定持有锁？为什么？

需要一点提示

考虑队列里线程醒来时，是否还可能有新的线程刚好抢到了 state。

查看参考答案（建议先尝试）

不是。unpark 只让线程有机会继续执行；B 还必须调用实际的获取逻辑并满足状态条件。尤其在非公平锁中，其他线程可能抢先获得资源，因此 B 可能继续等待。

问题 2：看到 state = 2，能否断言“锁被两个线程同时持有”？

查看参考答案

不能。state 的业务含义由具体同步器定义。在 ReentrantLock 中通常是同一线程重入持有的次数；在 Semaphore 中一般是当前可用许可数量，不能只看数字推断“持有锁的线程数”。
