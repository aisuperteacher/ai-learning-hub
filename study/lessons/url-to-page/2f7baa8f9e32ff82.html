01

URL 到底包含什么？

URL（Uniform Resource Locator，统一资源定位符）就是资源的定位描述。它不只是域名，还是告诉浏览器应该使用什么协议、访问哪个路径，以及附带什么参数。

URL ≠ IP 地址

域名对人友好；真正建立网络连接时通常还要得到目标 IP，或按代理配置把目标交给代理处理。

页面 ≠ 一张图片

HTML 描述结构，CSS 描述外观，JavaScript 描述行为，图片和字体是其他资源。

还可能包含端口，比如 https://example.com:8443/。HTTPS 默认端口是 443，HTTP 默认端口是 80。URL 的片段标识符（#reviews）通常由浏览器处理，不作为 HTTP 请求目标发送给服务器；而 ?color=red 通常会出现在请求目标中。

输入的不一定就是 URL：地址栏也可能把文字当作搜索词。浏览器会按地址栏策略判定。若 URL 含用户名或密码也不代表适合安全使用；实际应用不应把凭据写入查询字符串。
02

真正上网前，浏览器先做什么判断？

按 Enter 后，浏览器首先判断这次导航属于什么类型，是否能直接使用已有状态。现代浏览器通常使用多个进程：管理导航和窗口的浏览器进程、处理网络的相关组件、负责解析和渲染页面的渲染器进程。具体进程分工因浏览器实现而异。

  1. 判定导航：是整页导航，还是当前文档里的 #reviews 片段变化？历史记录后退是否可以用 BFCache（后退/前进缓存）恢复？
  2. 安全与策略：遵守浏览器安全规则，例如 HSTS 已知站点可以先把 HTTP 升级为 HTTPS；也可能遇到证书或安全内容阻止。
  3. 缓存或离线拦截：受 Service Worker 控制的页面，导航请求可能由它返回缓存响应；HTTP 缓存也可能直接满足请求、或要求向服务器确认资源是否变化。
  4. 连接复用：即使需要新请求，若已有可用且符合条件的连接，也不一定重新建 TCP/TLS。
缓存或机制它保存什么影响哪个阶段
DNS 缓存域名解析结果（及其有效期）可能免去向外部 DNS 服务器查询
HTTP 缓存某个响应的资源内容与元数据直接复用资源，或条件请求获 304
Service Worker + Cache Storage受站点脚本控制的缓存条目可能拦截页面或资源请求
BFCache适用页面的完整文档及执行状态历史前进后退可能直接恢复页面
已有连接 / TLS 会话可重用连接 / 恢复信息节省握手往返

注意：浏览器访问过某个站点不等于全部资源必定缓存；也不等于页面一定从缓存读取。是否可用依赖响应头、缓存分区、安全策略和浏览器状态。

03

DNS：域名如何变成可以连接的地址？

DNS（Domain Name System，域名系统）负责把域名映射到可用于连接的信息。可以把它理解为网络的“通讯录”，但它不只返回一个 IP，也能通过别名或其他记录支持复杂部署。

浏览器提出主机名
本地缓存先查记录
递归解析器代替客户端查找
根服务器指向顶级域
.com 服务器指向权威域
权威 DNS给出记录

真实的递归过程：如果缓存未命中，递归解析器可以先问根服务器“.com 去哪里查”，再问 .com“example.com 谁负责”，最后向该域的权威服务器查询所需记录，并把结果返回给浏览器/系统。客户端通常不必亲自逐个向根服务器发送请求。

  • A 记录：给出 IPv4；AAAA：给出 IPv6。
  • CNAME：给出别名，解析时可能进一步查到真实目标记录。
  • TTL：记录的缓存存活时间；不是服务器必须在这个时间内响应的意思。
  • DoH / DoT：DNS 查询可以经过加密通道，具体是否使用取决于配置。
  • CDN 场景：DNS 可能把域名指向 CDN 的接入地址，而非真实业务服务器的 IP。
为什么需要 DNS？IP 可以变化，后面还可能有多个服务器、不同地区接入点。只让用户记住域名，维护方就能调整指向，而无需修改用户收藏的网址。
04

有了 IP，数据到底怎样经过互联网？

网络通信不会让你的电脑直接把整份网页“抛到远端”。发送内容会按协议分成可传输的数据单元，经过链路和路由器转发。

  1. 本机：操作系统根据路由表决定使用哪块网卡、下一跳是谁（比如家用路由器或 VPN 设备）。
  2. 局域网：以太网或 Wi-Fi 需要找到下一跳的链路层地址。IPv4 通常通过 ARP，IPv6 通过邻居发现机制（NDP）。注意查的是下一跳的地址，不是远在互联网另一端的服务器 MAC。
  3. 网络出口：家庭路由器可能使用 NAT 转换内网地址；公司代理、VPN 也可能改变路径。
  4. 互联网：路由器依据目标 IP 逐跳转发，直至到达目标或相关接入服务；不同报文未必走完全一样的路。
类比边界：把互联网想成快递网有助于理解“地址与中转”，但真实数据包不是一个一个按人工规划路径送货：路由、重传、拥塞控制、分片与加密都有自己的协议机制。
05

TCP 三次握手、TLS 加密与 HTTP/3，分别做什么？

路线 A：HTTPS over TCP（HTTP/1.1、HTTP/2 常见）

TCP（传输控制协议）为双方提供可靠、有顺序的字节流。新建连接时通常执行三次握手：

客户端                              服务端
   | -------- SYN --------------> |  ① 我想建立连接
   | <------ SYN + ACK ---------- |  ② 收到，我也准备好了
   | -------- ACK --------------> |  ③ 确认
          TCP 连接建立

为什么不是“只发一次消息”就完事？握手让双方建立连接状态、协商初始序列等信息，避免在双方尚未确认通信意图与可达性时直接把后续可靠传输当成已经成立。

TCP 连接建立以后，HTTPS 还需要 TLS（传输层安全协议） 协商加密参数、验证服务器证书、形成用于保护通信的会话密钥。TLS 1.3 通常比旧版本握手更精简；恢复连接时可能进一步节省往返。

路线 B：HTTP/3

HTTP/3 不把 HTTP 放在 TCP 之上，而是使用 QUIC（基于 UDP 的现代传输协议），其安全握手集成 TLS 1.3。QUIC 自己实现可靠交付、流与拥塞控制等能力，常使用 UDP 443。

对比HTTP/1.1、HTTP/2（常见 HTTPS）HTTP/3
底层TCP + TLSQUIC over UDP（内建 TLS 1.3）
TCP 三次握手新 TCP 连接需要不需要 TCP 握手
可靠性主要由 TCP 提供由 QUIC 提供
多个请求HTTP/2 在一条连接上多路复用QUIC 多路流；一条流丢包不必阻塞所有流的数据交付
是否始终更快否，取决于网络与负载也否，可能有 UDP 受限或回退等情况

证书为什么重要？

浏览器会依据其信任体系验证证书链、证书适用的域名及有效期等。TLS 让应用数据在传输途中具备机密性和完整性，防止普通中间节点直接读取或篡改 HTTPS 的请求内容。但 DNS 信息、对端 IP 等并不总是隐藏；TLS 也不代表网站业务逻辑一定可信。

此外，HTTPS 的目标可能是 CDN 边缘节点：浏览器与 CDN 建立 TLS，而 CDN 与源站是另一段连接。不能想当然地把“浏览器证书对应的服务器”当成后端 Docker 容器。

一个常见误区：“HTTPS = TCP 三次握手 + TLS，且每个请求都重复一次”。HTTP/3 不使用 TCP；已有 TCP / QUIC 连接也可能被复用。
06

HTTP 请求与响应：双方实际说了什么？

HTTP（超文本传输协议）是客户端与服务端交换请求、响应的规则。无论 HTTP/1.1、2、3 使用哪种线上的编码方式，核心语义类似：方法、目标、头部、状态、消息内容。

为了教学，下面用 HTTP/1.1 的可读文本形式表示请求
GET /products/42?color=red HTTP/1.1
Host: www.example.com
Accept: text/html
Accept-Encoding: gzip, br
Cookie: session=example-placeholder
User-Agent: ExampleBrowser/1.0

GET 表示读取资源；Host 指明目标主机；Accept 表明浏览器可接收 HTML；Cookie 只有在适用域名、路径与浏览器策略等条件满足时才携带。示例 Cookie 是虚构占位数据。

关键观察：请求目标包含 /products/42?color=red，但不包含 #reviews。片段一般由客户端导航与页面逻辑处理。
服务端返回的响应（同样是教学示例）
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Cache-Control: max-age=60
ETag: "product-42-v7"
Content-Encoding: br

<!doctype html>
<html>...商品页面的 HTML...</html>

状态码 200 表示成功；301/302/307/308 常见于重定向；304 用于告诉客户端缓存版本仍可使用（不是普通的跳转地址）；404 表示资源不存在；500 表示服务端内部错误。

缓存中的 304 是怎么回事？

# 客户端已有过期但可验证的缓存
GET /products/42?color=red HTTP/1.1
Host: www.example.com
If-None-Match: "product-42-v7"

# 如果仍是同一版本，服务器可能返回
HTTP/1.1 304 Not Modified
ETag: "product-42-v7"

# 不用重新下载完整响应正文；客户端复用已有内容。

浏览器第一次收到 HTML 后，不必等全部正文下载完成才开始处理：它通常可以边接收字节边解析，这也是流式 HTML 有价值的原因。

07

请求到达服务器后，如何找到真正的业务代码？

以一种常见网站部署为例，网络请求可能经过下面这条链路。真实系统并不要求每层都存在：

浏览器HTTPS 请求
CDN / WAF缓存与过滤
Nginx反向代理
应用服务业务逻辑
Redis / DB读取数据
响应返回HTML / JSON
  1. CDN（内容分发网络）：如果边缘缓存命中且规则允许，可能直接返回页面或静态资源；否则回源。WAF 可以基于策略检查请求，拦截恶意流量。
  2. 负载均衡 / Nginx：根据域名、路径、负载等规则，把请求转给合适的应用实例。反向代理隐藏了内部服务布局，并可做压缩、TLS 终止、日志等。
  3. 应用层：例如 Java Spring Boot、Node.js、Go、Python 等服务接收请求，判断路由、校验登录态和权限、执行商品查询逻辑。
  4. 数据层：根据业务需要，从 Redis 等缓存、MySQL 等数据库、对象存储或其他服务取数据，组成返回结果。
  5. 生成响应：返回完整 HTML（服务端渲染）、HTML 外壳 + JS（客户端渲染），或 JSON / 文件等。

服务端渲染 SSR 和客户端渲染 CSR 有何区别？

SSR · 服务器先组织 HTML

首份 HTML 可以直接包含商品标题和价格。浏览器较早看到内容；但后续动态交互可能仍要加载 JS 并完成 Hydration（注水/激活）。

CSR · 浏览器用 JS 组织页面

服务器先返回基础 HTML 和 JS，浏览器运行脚本、请求接口数据后生成页面主体。资源或脚本失败时可能出现空白或不完整页面。

不要误解为“HTML 必须来自应用服务器”。它可以是源站静态文件、CDN 的缓存、SSR 动态结果、流式结果，也可能被 Service Worker 提供。后端返回 JSON 也不意味着浏览器会自动把它画成网页。
08

浏览器拿到 HTML，怎样构建 DOM？

HTML 是带标签的文本，浏览器不会把字符 <h1> 原样画到屏幕上，而是将字节解码、按 HTML 语法切分为令牌（Token），再构造 DOM（Document Object Model，文档对象模型） 树。

<!doctype html>
<html>
  <head>
    <link rel="stylesheet" href="/style.css">
    <script defer src="/app.js"></script>
  </head>
  <body>
    <h1>我的商品</h1>
    <p>价格：100 元</p>
  </body>
</html>
Document
└─ html
   ├─ head
   │  ├─ link (CSS 文件)
   │  └─ script (JS 文件)
   └─ body
      ├─ h1
      │  └─ 文本节点：我的商品
      └─ p
         └─ 文本节点：价格：100 元

为什么需要 DOM？因为页面不是一条纯字符串，而是具有父子、顺序和属性关系的可变结构。JavaScript 可以使用 DOM API 查找、修改节点。例如把商品价格的文本更新成“优惠价”。

浏览器通常能流式解析 HTML，还可能通过预加载扫描器较早发现图片、CSS、JS 的 URL，提前发起资源请求，并不是必须把整个 HTML 接收完成才开始动作。

HTML 解析遇到没有特殊属性的经典同步 <script src="..."> 时，通常会暂停解析等待其下载和执行；defer、async、type="module" 的执行时机则不同。
09

为什么一个网页要产生几十甚至几百个请求？

HTML 往往只包含指向其他资源的引用，浏览器需进一步获取 CSS、JavaScript、图片、字体、视频以及通过接口得到的数据。不同资源可能有不同域名，因此还会引入新的 DNS 查询与连接。

浏览器发现产生的动作页面后果
<link rel="stylesheet">请求 CSS，解析成 CSSOM决定元素颜色、大小、布局规则等
<script src="...">请求并执行 JS运行逻辑；可能改变 DOM / 继续发请求
<img src="...">请求、解码图片显示图片；没预留尺寸可能触发布局移动
@font-face按需要下载字体影响文字外观与可能的布局
fetch('/api/product/42')JS 发 HTTP 请求获取数据动态更新页面；受同源策略 / CORS 等影响

资源可以并行加载，但优先级、协议、缓存和 JavaScript 执行依赖决定实际顺序。CSS 通常与首屏渲染关系密切；普通图片可能晚到；被标记为懒加载的图片可能在滚动到附近时才请求。

为什么不会把所有资源放在一个文件？模块化、复用、独立缓存、按需下载和维护成本都有价值。但过多依赖仍可能拖慢首屏，这是工程上的权衡。

最关键的后半程：文本如何变成像素？

这段被称为 关键渲染路径（Critical Rendering Path）。它不是“显示 HTML 原文”，而是将结构、样式和视口条件转成屏幕能显示的内容。

HTML → DOM
树形结构
CSS → CSSOM
样式规则
样式计算 / 渲染结构
哪些元素参与渲染？每个元素是什么样式？
↓
Layout 布局
计算大小、坐标、换行与盒子的位置
↓
Paint 绘制 / Raster 光栅化
描述绘制内容并把图形转成像素
↓
Compositing 合成 → 显示
组合图层，提交画面；由显示系统呈现
  1. CSSOM：浏览器解析 CSS 选择器和声明，形成可以用于样式匹配与计算的结构。h1 { color: red } 就表示相应标题应该使用红色文本。
  2. Style / Render Tree：浏览器把 DOM 和样式信息结合，计算可渲染对象。display: none 的元素通常不产生相应渲染盒，但仍可能存在于 DOM。
  3. Layout（布局）：结合视口尺寸、字体、盒模型、Flex/Grid 等规则计算元素的长宽和位置。
  4. Paint（绘制）：生成背景、文字、边框、阴影等绘制信息，并在光栅化中转成像素。
  5. Composite（合成）：浏览器可能把一些内容放在独立图层，合成成最终画面。GPU 经常参与其中，但实现细节不只有 GPU。

一个能立刻理解的例子

改变 width: 100px 为 200px

可能改变盒子的几何大小，需要重新布局，之后可能重新绘制、合成。

改变 transform: translateX(20px)

在合适的图层条件下，可能主要通过合成移动元素，不必重新布局；并非任何场景都能保证只走合成。

反例：页面 DOM 已生成 ≠ 页面已经可见；已经可见 ≠ 图片全部加载；图片全部加载 ≠ JavaScript 逻辑已能快速响应。

JavaScript、事件循环与“能点得动”之间的关系

JavaScript 运行时可以添加事件监听器、发接口请求、创建节点和修改样式。浏览器负责把相关工作排进合适的任务调度机制。常见页面脚本在渲染器主线程执行；长时间同步任务会让主线程无法及时处理用户交互与绘制。

事件 / 指标实际含义不要误以为
DOMContentLoadedHTML 已解析完成，并执行完所需的 defer / module 脚本所有图片都必须加载完才触发
load页面及其需要等待的相关资源已加载完成后台异步请求、懒加载资源都已完成
FCP（首次内容绘制）首次绘制文本、图像等内容之一页面所有重要内容已显示
LCP（最大内容绘制）视口里最大相关内容元素完成绘制的时间永远代表用户已可交互
INP（交互到下一次绘制）观察页面交互响应延迟的 Core Web Vitals 指标只有网络请求影响点击速度
CLS（累计布局偏移）衡量页面意外的可见布局移动布局动了就一定是网络故障

比如页面按钮已经画出来，但初始化脚本正在执行一个耗时 2 秒的同步任务，那么用户点击后可能迟迟得不到响应。反过来，一个原生 HTML 链接可以不依靠大量 JS 就完成跳转。

浏览器之后还在不停工作

滚动、动画、定时器、用户输入、WebSocket 消息、接口响应都会触发后续更新。更新可能只需要合成，也可能导致重新计算样式、布局与绘制。所以“页面显示出来”不是执行链的绝对终点。

12

五种路径变体，彻底打破死记流程

① 首次访问

可能需要 DNS → 新连接 → 请求 → 服务端响应 → 解析与绘制。仍可能使用预连接等优化。

② 再次访问

DNS 和连接可能命中缓存；资源可直接命中 HTTP 缓存，也可能发 If-None-Match 得到 304。

③ 只改 #hash

如果是同一文档内的片段导航，通常没有新的文档网络请求，主要涉及 URL 历史状态与滚动。

④ SPA 内部路由

JavaScript 可用 History API 更新 URL，并局部渲染视图；可能请求 JSON，不需要重新下载整页 HTML。

⑤ 301 / 302 重定向

服务器先回复新的 Location，浏览器再发起目标导航；跨域可能重新解析 DNS、重新连接。

⑥ 离线 / Service Worker

受控制的页面可以由 Service Worker 返回已存内容。是否可离线使用取决于站点实现，不是默认保证。

记住：性能分析里的“DNS 耗时 0ms”不代表互联网没有 DNS；“未观察到 TCP 握手”也不代表 HTTP 无须连接。它们可能已经被缓存、复用或采用了 QUIC。

亲自验证：用 Chrome DevTools 观察真实链路

建议在 Windows 的 Chrome 浏览器中操作。目标先选择公共测试页 https://example.com/；教学 URL 的 /products/42 不需要真的访问。

  1. 打开一个正常网站，按 F12（或 Ctrl + Shift + I）进入开发者工具。
  2. 进入 Network（网络） 面板，勾选 Preserve log（保留日志），然后刷新页面。
  3. 点击类型为 document 的主文档请求，依次看 Headers（请求地址、状态码、响应头）、Timing（网络耗时）、Response（响应正文）。
  4. 观察 Initiator 与 Waterfall：哪些资源由 HTML 解析器发现，哪些由脚本触发？是否并行？
  5. 保持面板打开，分别在勾选与取消 Disable cache（停用缓存） 时重新加载页面。比较 Size、Status、Timing。注意该选项主要控制开发者工具环境下的 HTTP 缓存，不等于关掉所有缓存。
  6. 切到 Performance 面板录制一次刷新，找与脚本、布局、绘制相关的工作，再思考为什么“网络加载完成”不等于“渲染完成”。

一个关键的安全例子：HTTPS 页面被重定向了

如果地址栏从你的 HTTPS 域名跳到了另一个站点，不能直接断言“DNS 被污染”。需要先看 HTTP 层是否有 3xx 的 Location，是 CDN、反向代理还是业务服务返回的；如果没有相应网络重定向，还要排查页面 JavaScript 的 location 导航、浏览器扩展、Service Worker、恶意或错误本地代理等。

为什么这种区分重要？DNS 决定向哪里连接，HTTP Location 决定浏览器下一步跳往哪个 URL，JavaScript 则可能在页面加载后主动触发跳转。不同层的问题，不应该用同一种修复方法。

问题 1 · 条件变化

页面已经打开，仅把地址里的 #intro 改成 #reviews。为什么一般不需要重新 DNS、建连接和下载整个 HTML？

查看提示

思考这是否仍是同一个 Document，URL 的片段是否会随 HTTP 请求发给服务器。

参考解释

同一文档的片段导航通常只改变浏览器定位、历史状态或滚动目标；fragment 不在 HTTP 请求目标中，不需要为此发出新的文档请求。但页面脚本可能监听变化并自行触发接口请求，不能据此说绝不会发生网络流量。

问题 2 · 为什么

网络面板显示商品接口返回了 200 和 JSON，但页面依然白屏。你会先查哪里？为什么 HTTP 成功不代表页面已经渲染成功？

查看提示

把服务器交付数据和浏览器执行 JS、构建 DOM 分开考虑。

参考解释

先查 Console 是否有 JS 错误，再看 Network 的脚本资源、XHR/Fetch 是否有失败；检查 Elements 是否创建出预期 DOM、CSS 是否隐藏了内容、CSP 是否拦截。200 只说明本次 HTTP 请求成功，不能证明页面脚本已执行、数据被正确处理或像素已绘制。

为什么一个网页第二次打开会更快？请说出至少三种可能机制，并解释为什么不能保证第二次一定快。

区分地址查询、连接握手、资源传输和浏览器渲染四种开销。
